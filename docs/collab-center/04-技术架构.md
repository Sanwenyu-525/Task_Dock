# 04 · 技术架构设计

## 1. 总体架构

```
┌────────────────────────── 前端（React 19 + TS）──────────────────────────┐
│ 规划中心 · 协作视图  CollabWorkspace                                     │
│   ├ IssueBoard / IssueDetail        ├ PlanReviewPanel                    │
│   ├ VisualViewer（SVG / 标注 / 原型） └ VersionDiffView                   │
│ 状态：CollabPanel 组件本地状态（请求代际丢弃迟到响应）                      │
│ IPC：src/lib/collab.ts（typed invoke，错误 normalize）                     │
└──────────────────────────────────────────────────────────────────────────┘
                                   │ Tauri IPC
┌────────────────────────── Rust 服务层（src-tauri/src/collab/）────────────┐
│ commands.rs（参数校验 → Actor::ui → service）                             │
│ service.rs（门面：ProjectContextService / IssueService / PlanService /     │
│             VisualizationService / EvidenceService / AuditService）        │
│ ├ issue.rs      需求与 Bug（去重、状态、关联、解决/验证）                   │
│ ├ plan.rs       方案状态机、审批、任务拆解、进度                            │
│ ├ visual.rs     文档/版本/差异/校验/导出/渲染器注册表                       │
│ ├ prototype.rs  原型 DSL、Patch、事件状态机、交互流校验                     │
│ ├ ai.rs         Provider trait + Registry + Job 执行                       │
│ ├ context.rs    项目上下文装配（分页/字段过滤）                             │
│ ├ actor.rs      Actor / Capability / 权限判定 / 审计                        │
│ └ schema.rs     MIGRATION_77（8 张表）                                     │
└──────────────────────────────────────────────────────────────────────────┘
                                   │
             ┌─────────────────────┼─────────────────────┐
             ▼                     ▼                     ▼
    既有 planning / tasks     SQLite（唯一事实源）     MCP 接入层
    *_inner 服务函数          WAL + 单写者 + revision   src-tauri/src/collab/mcp_tools.rs
```

**入口一致性**：IPC、MCP（以及后续 CLI/REST）只做「参数解析 → Actor 推导 → 调 service → 结果封装」。
业务规则只在 `collab::service/*` 内实现，**不在入口层写 SQL**。

## 2. 模块边界

| 模块 | 负责 | 不负责 |
|---|---|---|
| `issue.rs` | Issue/Bug 的字段、去重、关联、状态 | 方案审批、可视化 |
| `plan.rs` | 方案状态机、审批、任务拆解；从 Issue 建方案时按规则落 2 条可执行草案（实现/验证） | 任务本身的生命周期（归 tasks） |
| `visual.rs` | 文档 Schema、版本、diff、导出、安全 | 文件复制/回收站（归 evidence/fsops） |
| `assets.rs` | 可视化资产：导入、SHA-256 去重、受控读取、归档 | 证据系统（`collab_evidence`）职责 |
| `prototype.rs` | 原型组件 DSL、批量 patch（含页面级操作）、交互状态 | 任意 HTML/JS 执行 |
| `ai.rs` | Provider 抽象、生成任务、失败记录 | 直接写业务表（结果经 service 校验后落库） |
| `context.rs` | 跨域只读聚合、分页 | 写任何数据 |
| `actor.rs` | 身份、能力、审计写入 | 业务校验 |
| `commands.rs` | Tauri 参数/返回、Actor=UI | 业务规则 |
| `mcp_tools.rs` | Tool schema、Agent Actor、错误映射 | 权限白名单重建 |

## 3. 数据流

### 3.1 写路径（以创建需求为例）

```
MCP tools/call
 → collab_tools::call → actor::from_mcp(ctx.agent, project_id)
 → actor.require(Capability::IssuesWrite) + project grant check
 → issue::create_issue(db, actor, input)
     ├ 校验字段（长度/枚举/JSON 数组）
     ├ 检查项目存在（planning_projects）
     ├ 去重键 dedupe_key = normalize(title)+kind
     ├ 事务：INSERT issue + INSERT audit
     └ 返回 Issue（含 duplicate_candidates）
 → JSON 结果（成功/错误统一结构）
```

### 3.2 读路径（项目上下文）

`ProjectContextService::get(project_id, scope, page, fields)` 并行（顺序查询即可，量小）读取：
`planning_projects` + `project_stats_from` + `collab_issues` 计数 + `collab_plans` 列表 +
`tasks` 关联 + `collab_visual_docs` 列表；按 scope 裁剪正文；按 fields 过滤键；上限 200 条/域。

## 4. 统一可视化引擎

### 4.1 文档格式

```json
{
  "id": "vd_…", "projectId": "pp_…", "planId": "pl_…",
  "title": "登录流程", "description": "",
  "kind": "flowchart | architecture | dataflow | prototype | bug_annotation | static_image | diff",
  "schemaVersion": 1,
  "sourceFormat": "json | mermaid | image | svg",
  "sourceContent": "{…}",           // 可重新编辑的结构化内容
  "renderer": "graph-svg | prototype-react | image | annotation",
  "previewAsset": "collab-assets/…", // 可选，静态图或导出缓存
  "status": "draft | published | archived",
  "version": 3, "revision": 5,
  "createdBy": "…", "updatedBy": "…", "createdAt": "…", "updatedAt": "…"
}
```

### 4.2 Schema（每类）

| kind | sourceContent | 校验要点 |
|---|---|---|
| `flowchart` | `{nodes:[{id,label,kind?,config?}],edges:[{id,from,to,label?}],layout:{direction}}` | 节点 id 唯一；边引用存在；≤200 节点/400 边；label ≤200 |
| `architecture` | 同上，`nodes[].kind=module/service/store/ui/external` | 同上；kind 白名单 |
| `dataflow` | 同上 + `nodes[].io` | 同上 |
| `prototype` | `{viewport:{width,height},pages:[{id,name,components:[…]}],state:{…}}` | 见 §5 |
| `bug_annotation` | `{image:"asset path",annotations:[{x,y,w,h,note,severity}]}` | 图片必须在应用数据目录；标注在图片范围内 |
| `static_image` | `{asset,width,height,params}` | 扩展名白名单；≤32MB |
| `diff` | 由 diff 服务生成，不允许用户创建 | 只读 |

### 4.3 RendererRegistry

`RendererRegistry` 是静态能力表，不动态注册任意代码：

```rust
pub struct RendererCapability {
    pub kind: &'static str,
    pub renderer: &'static str,
    pub interactive: bool,
    pub editable: bool,
    pub export_formats: &'static [&'static str],
}
pub fn list_renderers() -> &'static [RendererCapability];
pub fn resolve(kind: &str) -> AppResult<&'static RendererCapability>;
```

前端 `VisualViewer` 按 `renderer` 选择组件；未知 renderer 显示「不支持的类型」而不是白屏。

### 4.4 版本与 diff

- 每次 `create/update/restore/patch` 在一个事务内：更新文档（version+1、revision+1）+ 插入版本快照 + 审计。
- 快照保存完整 `sourceContent` 与元数据，不依赖外部文件；静态图快照保存 asset 引用 + sha。
- `diff` 按 kind 做结构比较：
  - 图：节点/边集合差异 + label/config 变化；
  - 原型：页面/组件集合差异 + props/style/events 变化；
  - 文本字段（title/description）：逐字段变化。
- 输出 `{added,removed,changed,items[],summary}`；不做像素级 diff（无渲染依赖）。

### 4.5 导出

| 类型 | 支持 | 实现 |
|---|---|---|
| 图（3 类） | SVG | 服务端生成 `<svg>`（节点矩形 + 折线 + 文本，坐标由简单分层布局计算） |
| 原型 | JSON | 完整 DSL + 版本号 |
| 标注 | JSON | 图片引用 + 标注 |
| 静态图 | 原文件路径 | 校验后返回 |
| 位图导出 | **不支持** | 返回 `UNSUPPORTED`，说明需要前端 canvas（未实现，不伪造） |

## 5. 原型系统

### 5.1 组件白名单（DSL）

```json
{"id":"c1","type":"button","x":16,"y":80,"w":120,"h":36,
 "props":{"label":"提交","variant":"primary"},
 "style":{"bg":"var(--accent)","radius":"8px","fontSize":"14px"},
 "events":{"onClick":{"action":"navigate","target":"page-2"}}}
```

允许 `type`：`frame,text,heading,button,input,switch,tabs,list,image,badge,divider,chart`。
- `style` 只允许：`bg/fg/radius/fontSize/fontWeight/padding/gap/align/border`；值必须是
  `var(--…)`、hex、`Npx`、数字或枚举；**禁止**任意 CSS 字符串/URL/expression。
- `events` 允许 `onClick/onChange/onSubmit` → `{action:navigate|openModal|closeModal|toggle|setValue,
  target?, value?}`。
- 限制：≤20 页，≤200 组件/页，坐标 0–5000，宽高 1–2000，字符串 ≤500。

### 5.2 交互状态机

服务端 `dispatch_event(state, event) -> state'`：
- `navigate` → `currentPage=target`
- `openModal/closeModal` → `modal=target|null`
- `toggle` → `state.values[target] = !current`
- `setValue` → 写入 `value`
非法目标/未知动作返回 `VALIDATION`，不改变状态。前端用同一套逻辑做即时模拟（纯函数，
无 eval）。**状态不落库**（模拟态是会话级的），文档只保存初始 `state`。

事件优先级（2026-11-21）：**组件显式配置的事件优先**；未配置时只给开关（`toggle` 自身）与
输入框（`setValue` 自身）提供默认行为，其余组件不猜动作。预览与编辑共用 `PrototypeRenderer`，
因此本地模拟与服务端拿到的 `ProtoEvent` 完全一致；目标不存在时本地与服务端都返回明确错误
（前端展示在预览工具条下方）。

### 5.2.1 Patch 语义（2026-11-21）

```json
{"op":"update","pageId":"page-1","componentId":"button-1",
 "patch":{"style":{"radius":"8px"}},
 "removeKeys":{"style":["bg"],"events":["onClick"]}}
```

- 增量 merge 保留，新增 `removeKeys` 表达删除；同一键既删又写时以 `patch` 为准；
- 删除不存在的键是幂等空操作（diff 可重复应用）；`removeKeys` 只接受 `props/style/events`，
  `style`/`events` 操作只能携带自身段名；
- `id`/`type` 永远拒绝；坐标与对象段之外字段一律拒绝；
- 一次 Patch 的所有操作先在内存内容上执行完，再统一 `normalize_content` 校验并落库；
  任一步失败则整个 Patch 不保存、不产生版本（`visual::update_document` 是唯一写入口）。

### 5.3 安全沙箱（结构化渲染优先）

- 不执行 HTML/JS；不使用 `dangerouslySetInnerHTML`；不 `eval`/`new Function`。
- 图片只允许应用数据目录内的 asset（由后端返回 `asset://` 或本地路径），禁止 http(s) 外链。
- 渲染层加容器边界（`overflow:hidden`）、资源上限、组件数量上限。
- 若未来必须支持 HTML/JS：使用独立 WebView/受限 iframe + 严格 CSP + postMessage 白名单，
  **本轮不实现**（见 `07-安全与性能.md`）。

## 6. AI Provider

```rust
pub trait ModelProvider: Send + Sync {
    fn name(&self) -> &'static str;
    fn capabilities(&self) -> ProviderCapabilities; // text/image
    fn generate_text(&self, req: TextRequest) -> Result<TextResult, AiError>;
    fn generate_image(&self, req: ImageRequest) -> Result<ImageResult, AiError>;
}
```

- 默认注册 `local-structured`：**确定性规则生成**（不是模型），从方案/需求生成流程图、架构图、
  原型骨架；输出标注 `provider=local-structured`，UI 明示「本地规则生成」。
- `external-openai-compatible`：保留 trait 与配置读取，但当前**无 HTTP 客户端**，未配置或未启用时
  返回 `PROVIDER_UNAVAILABLE`（可读原因），不产生假结果；列入 P1。
- 生成流程：`ai::generate_visual` → provider → `visual::validate_and_normalize` → 成功才落库并生成版本；
  失败写 `collab_ai_jobs(status=failed, error_code/message)`。
- 图像 job：状态 `queued → running → succeeded|failed|cancelled|provider_unavailable`；
  状态转换写库；`cancel` 只对 queued/running 有效；成本 `cost_units` 默认 0。

## 7. 文件与证据存储

```
<app_data>/collab-evidence/<project_id>/<issue_id>/<sha256-prefix>-<safe-name>
<app_data>/collab-assets/<project_id>/<doc_id>/<sha256-prefix>-<safe-name>
```

- `evidence::attach_path`：校验扩展名/大小 → 复制 → sha256 → 同 sha 幂等返回既有记录。
- `evidence::attach_text`：日志/堆栈写入 `.txt`，≤1MB。
- 路径规范化（拒绝 `..`、绝对路径逃逸、符号链接）；只允许文件、不允许目录。
- 证据记录不可通过文件工作区删除；归档只改状态（本轮无删除命令）。

## 8. 权限体系

| Capability | UI | Agent（MCP 映射） | 说明 |
|---|---|---|---|
| `IssuesRead` | ✓ | `plans.read` | 读需求/Bug |
| `IssuesWrite` | ✓ | `plans.write` | 创建/更新/归档/关联/解决 Bug |
| `PlansRead` | ✓ | `plans.read` | 读方案 |
| `PlansWrite` | ✓ | `plans.write` | 创建/编辑/提交审阅 |
| `PlansReview` | ✓ | **永不** | 批准/驳回/验收 Bug |
| `VisualRead` | ✓ | `plans.read` | 读图/原型 |
| `VisualWrite` | ✓ | `plans.write` | 创建/修改/版本恢复 |
| `EvidenceWrite` | ✓ | `plans.write` | 上传证据 |
| `AiGenerate` | ✓ | `plans.write` | 请求生成 |

- Agent 还需通过项目授权（`mcp_agent_grants`）；跨项目一律 `PERMISSION_DENIED`。
- 审批额外校验 `actor.kind == Ui`；直连 SQL/命令都无法绕过（命令层不接受 actor 参数）。

## 9. 版本与并发

- 所有可写实体带 `revision INTEGER`；更新必须传 `expected_revision`，不匹配返回
  `CONFLICT` + 当前 revision（不静默覆盖）。
- 可视化另带 `version`（内容版本）；恢复历史 = 用旧快照写入新版本。
- 审计表记录 `revision_before/after`、actor、source、action、时间；只增不改。
- 事务：`Db::with_transaction` 内完成「校验 + 写实体 + 写版本 + 写审计」，任何失败整体回滚。

## 9.1 创作工作台分层（2026-11-20）

人工与 AI **共用同一条写入链路**：

```
前端编辑器（GraphEditor / PrototypeEditor / ImageAnnotator）
        │  只产出结构化内容或批量 Patch
        ▼
src/lib/collab.ts（类型化 IPC）
        │
        ▼
Core（权限、项目归属、事务、审计）
        │
        ├── Validation      schema.rs / visual.rs / prototype.rs / assets.rs
        ├── DocumentService visual::create_document / update_document
        ├── VersionService  visual::write_version（每次正式保存 +1）
        ├── AssetService    assets::import_asset / read_asset / archive_asset
        └── AI Provider     ai.rs（规则 Provider / 未来真实模型）
```

职责边界：

| 层 | 负责 | 不负责 |
|---|---|---|
| Renderer | 只读渲染：`GraphPreview`、`PrototypeRenderer`、`AnnotationRenderer` | 修改数据 |
| Editor | 编辑态：选择、拖拽、属性、撤销、页面管理；只在内存中改 | 直接写 SQLite |
| DocumentService | 读写文档、Schema 归一、revision/version | 渲染 |
| VersionService | 版本快照、恢复（生成新版本） | 删除历史 |
| AssetService | 图片导入、哈希去重、受控路径、受控读取 | 原型/文档内容 |
| AI Provider | 生成候选内容或候选 Patch | 直接落库（必须经 Core 校验与用户确认） |
| Validation | 结构、上限、白名单、安全字符 | 业务权限 |
| Core | 权限、项目归属、事务、审计 | 具体渲染 |

人工保存与 AI 应用保存都调用 `visual::update_document`（原型走 `prototype::apply_patch`），
因此版本号、revision 冲突、审计和导出行为完全一致。

## 9.2 编辑器与预览分离

- `PrototypeEditor`：编辑态，维护本地 `pages/components`，保存时把差异编译成一次批量 Patch；
  所有编辑（属性/位置/尺寸/页面/组件/样式/事件）统一走 `commitEdit(next, {fieldKey})`：
  一次用户操作一条历史，同一字段的连续输入按 1.5s 窗口合并，提交即清空 redo 分支，
  内容无变化不产生历史；
- `PrototypeRenderer`：纯渲染，按白名单组件映射 React 元素；
- `PrototypeInteractionSimulator`：预览态，调用 `collab_prototype_dispatch` 推进服务端状态机；
- `PrototypePropertiesPanel`：按组件类型渲染属性；
- `PrototypePageManager`：页面增删改名切换。

编辑态与预览态共用同一份 `sourceContent`；编辑态**不**执行事件，预览态**不**修改文档。
图片类文档：预览使用 `ImageRenderer` + `AnnotationRenderer`（无指针回调、无导入/保存/删除），
编辑使用 `ImageAnnotator`（导入、画选择/移动/缩放、改说明与严重程度、删除、保存）。

服务端对版本写入做**内容比对**：字段与规范化内容完全一致时直接返回当前文档，不写库、不产生版本、
不写审计；前端同时在 `!dirty` 时禁用保存并给出「没有需要保存的修改」。

## 9.3 图表编辑器数据约定

- 节点保存 `x/y`（0–5000）与可选 `color`；缺失坐标时服务端按方向生成确定性默认坐标，
  但**已有坐标绝不丢弃**；
- `layout.direction` 只允许 `TB/LR`，可选 `layout.width/height`（320–6000）；
- 节点/连线数量、ID 唯一性、连线端点存在性在归一化时校验；
- 拖拽仅更新前端内存，点击「保存」才写库并生成新版本。
