# 02 · 产品方案

## 1. 产品定位

TaskDock 的「协作与可视化规划中心」是 **Human + Agent 共用的需求与方案中枢**：

- 对外部 Agent：提供稳定的需求提交、Bug 上报、方案查询、可视化请求、任务获取、证据上传接口；
- 对开发者：提供可审阅的方案、可交互的原型、可对比的版本、明确的审批与验收动作；
- 对 TaskDock：把需求、方案、图、原型、任务、证据收束到同一条可追溯链路，形成长期项目记忆。

它不是「AI 生图按钮」，也不是「独立原型编辑器」，而是既有规划中心的**上层协作工作流**。

## 2. 用户角色

| 角色 | 身份来源 | 可做什么 | 不可做什么 |
|---|---|---|---|
| 本机开发者（Owner） | UI 本地用户 | 项目/需求/Bug/方案/原型/任务/证据全部操作；审批方案；验收 Bug | — |
| 外部 Agent（受限） | MCP Agent 行 / CLI 本机进程 / REST token | 读上下文；提交/更新需求与 Bug；提交方案；请求生成；获取任务；上传证据 | 审批方案、关闭 Bug、删除实体、跨项目访问 |
| 只读 Agent | capability=`*.read` | 读上下文、方案、图、任务 | 任何写入 |
| 系统（AI Job） | `ActorKind::System` | 写 AI 任务结果与生成版本 | 审批、删除、改任务状态 |

角色判定在服务端完成；调用方不能通过参数伪造 `actor`（IPC 只接受本机用户，MCP 由 Agent 行推导，
CLI 由本机进程 + `TASKDOCK_CLI_READONLY` 约束）。

## 3. 核心场景

1. **Agent 提需求**：Agent 读取项目上下文 → 提交 Issue（含影响范围/验收要求）→ 开发者在协作视图
   看到 → 一键生成方案草稿与流程图 → 审阅、修改、批准 → 拆解为开发任务 → Agent 获取任务并开发。
2. **Agent 报 Bug**：Agent 提交 Bug（日志/堆栈/截图/复现步骤/预期/实际/环境）→ 系统提示相似 Bug →
   开发者确认是否合并 → AI/本地生成定位图与修复方案 → 生成修复任务 → 修复后上传证据 → 验收关闭。
3. **开发者改原型**：打开方案关联原型 → 提出结构化修改（改文案/加组件/换布局/改交互）→ 服务端
   生成新版本 → 预览/对比 → 接受或回滚 → 关联方案更新。
4. **多 Agent 协作**：同一项目两个 Agent 分别提 Issue/Bug；审计记录来源、会话、时间；revision
   冲突返回 `CONFLICT` 与当前版本，不静默覆盖。
5. **能力关系图**：开发者在能力中心查看 Agent→Skill→MCP→工具的只读关系图，点击节点查看配置与
   调用记录（后续接入，本模块提供图渲染能力）。

## 4. 完整业务流程

### 流程 A：Agent 提交新功能

```
Agent → get_project_context（分页/字段过滤）
     → create_issue(kind=feature, 影响范围/验收要求)
     → [服务端] 权限校验 + 去重提示 + 落库 + 审计
     → generate_visualization(plan/issue, flowchart)（本地结构化或已配置模型）
     → create_plan(issue_id)（草稿）
     → submit_plan（待审阅）
开发者 → 协作视图审阅 → 修改/批注 → approve_plan（仅 UI Actor）
     → create_tasks_from_plan（生成 tasks + 关联）
Agent → list_tasks / update_task → 上传证据
开发者 → 验收 → 方案 completed
```

### 流程 B：Agent 提交 Bug

```
Agent → create_bug（描述/日志/堆栈/截图/复现/预期/实际/环境/文件位置）
     → detect_duplicates（相似提示，不自动删除）
     → attach_evidence（日志/截图，复制入库 + sha256）
     → generate_visualization(bug_annotation)（标注图）
     → create_plan(issue_id)（修复方案）
开发者 → 审阅 → approve → create_tasks_from_plan（修复任务）
Agent → 修复 → attach_evidence（修复证据）→ resolve_bug
开发者 → verify_bug（指定证据）→ closed
```

### 流程 C：修改原型

```
开发者打开原型 → 结构化指令/组件操作
 → apply_prototype_patch（服务端校验 + 新版本 + 审计）
 → 预览 → compare_versions / restore_version（恢复也生成新版本）
 → 方案关联保持
```

## 5. 页面与模块职责

| 页面/模块 | 职责 | 不做什么 |
|---|---|---|
| 规划中心 · 协作视图（新增数据源「协作」） | Issue/Bug 列表与详情、方案审阅、可视化查看、版本对比、证据 | 不替代原「我的项目/内置路线图」 |
| 方案详情 | 状态、审批、关联 Issue/图/任务/证据、进度 | 不直接编辑任务（跳任务中心） |
| 可视化查看器 | SVG 图渲染、节点详情、缩放、灯箱、原型交互、标注、版本/导出 | 不执行任意脚本 |
| 图表编辑器 | 节点/连线/属性/布局/画布尺寸/撤销重做/预览/导出 | 不做 Figma 级自由绘图 |
| 原型编辑器 | 组件增删改/拖动缩放/样式/事件/页面管理、编辑与预览分离 | 不执行任意 HTML/JS |
| 图片标注编辑器 | 资产导入、图片预览、矩形/圆形/箭头/文字标注层 | 不修改原始截图 |
| 能力中心（后续） | 关系图只读视图 | 不写能力数据 |
| 工作空间（后续） | 证据/原型文件关联、预览入口 | 不管结构化内容 |

## 6. 功能边界

**做**：
- 结构化图（flowchart/architecture/dataflow）、原型 DSL、Bug 标注、静态图引用、版本对比。
- 文本模型结构化生成（Provider 可替换；无模型时本地结构化生成）。
- 图像生成任务抽象（状态、取消、选择、关联、成本）。
- 需求/Bug/方案/证据/审批/任务拆解/审计。

**不做（本轮）**：
- 自由绘制画布（Figma 级）；
- 任意 HTML/JS 原型执行；
- 自动删除重复 Bug；
- Agent 自动批准方案；
- 远程网络访问与云端同步；
- 真实图像模型网络调用（无 provider 配置时明确不可用）。

## 7. 交互原则

1. **空状态不伪造**：没有数据就显示引导，不生成示例项目/假图。
2. **失败可恢复**：所有写入失败保留输入；AI 失败显示错误码与原因，不显示「成功」。
3. **审批可见**：方案卡片常驻状态徽标（草稿/待审阅/修改中/已批准/开发中/待验收/已完成/已归档）。
4. **版本可追溯**：每次保存显示版本号、修改者、来源、摘要；恢复有二次确认。
5. **宽窄屏**：沿用规划中心容器查询规则（<640 单列，≥640 左右分栏，≤460 看板改纵向）。
6. **可访问性**：图标按钮 `aria-label`，提示 `data-tip`，键盘可操作，Escape 关层。

## 8. 创作工作台（2026-11-20 增补）

### 8.1 核心原则：AI 与人工同权

每一种可视化内容都必须同时满足两条路径：

1. **人工从零创建**：从空白或模板开始，用图形界面添加、连接、布局、设置属性与交互并保存；
2. **AI 创建与辅助修改**：AI 生成完整内容或局部 Patch，经 Schema 校验、差异预览、用户确认后写入新版本。

人工与 AI **共用同一套 `VisualDocument` 数据模型、DocumentService、VersionService、审计与权限**；
不存在「AI 专用格式」或「人工专用表」。JSON 源码编辑只作为高级兜底，**不计为可视化编辑器完成**。

### 8.2 AI 创作

| 能力 | 输入 | 输出 | 确认要求 |
|---|---|---|---|
| 生成完整图表 | 项目/需求/方案/自然语言 | flowchart / architecture / dataflow 草稿 | 生成后进入编辑器，可继续修改 |
| 生成完整原型 | 需求/方案/描述 | prototype DSL 草稿（1–3 页白名单组件） | 同上 |
| 生成静态图片 | 提示词 | 图像 Job（未配置 Provider 时 `provider_unavailable`） | 不允许伪造成功 |
| 局部修改已有内容 | 文档 + 选中节点/组件 + 指令 | 候选内容（不直接落库） | 展示差异，用户确认后保存新版本 |
| 截图标注建议 | 图片 + Bug 描述 | 候选标注列表 | 用户逐条确认 |

- AI 修改现有文档时必须：读取当前版本 → 理解结构 → 生成候选 Patch/内容 → Schema 校验 →
  展示预览 → 用户确认 → 保存新版本。**禁止未经确认覆盖人工内容**。
- 无真实模型配置时保留 `local-structured` 规则 Provider，并明确标注「规则生成，非模型」；
  不允许把规则生成写成模型生成。

### 8.3 人工创作

- 创建空白文档、从模板创建。
- 图表：添加节点、拖动、删除、连线、改属性、改颜色、自动布局、调整画布尺寸。
- 原型：添加/删除/拖动/缩放/复制组件，改文案/颜色/字号/边框/间距/对齐/层级，
  新增/删除/重命名/切换页面，设置结构化交互事件。
- 图片：选择/导入文件、预览、缩放、裁剪、添加文字/箭头/矩形/圆形/重点标记。
- 每次明确保存生成一个新版本；拖拽过程不写库。

### 8.4 混合创作

| 场景 | 规则 |
|---|---|
| AI 创建 → 人工修改 | 文档 `authoring_mode=ai_generated`，人工保存的版本记录 `manual`，文档升级为 `ai_assisted` |
| 人工创建 → AI 补充 | 文档保持 `manual` 起点，AI 应用后升级为 `ai_assisted` |
| 人工选择部分节点交给 AI | 只把选中部分交给 AI；未选中内容必须保持不变 |
| AI 生成建议 → 人工决定 | 建议不落库；确认后走统一 `update_document` |
| 人工撤销 AI 修改 | 恢复历史版本，生成新版本，旧版本保留 |

### 8.5 创作来源字段

`authoring_mode` 与 `source_channel` 是两个正交维度：

- `source_channel` / `source`：从哪个入口发起（ui / mcp / cli / rest / ai / system）；
- `authoring_mode`：内容由谁创作（`manual` / `ai_generated` / `ai_assisted` / `agent_authored` / `imported`）。

例如 `source=ui + authoring_mode=ai_generated` 表示开发者从 UI 发起了 AI 生成。

## 10. 第二轮架构修复的用户可见变化（2026-11-21）

本轮不新增页面，只把「人工编辑 → 保存 → 追溯」这条链路补完整：

1. **编辑一定会被保存**：属性、位置、尺寸、页面名称、增删组件、样式、事件全部走同一编辑入口；
   连续输入合并为一次历史，不会每个字符生成一条撤销记录；保存时字段删除也会真正写回后端
   （`removeKeys`），不再出现「删了样式，重新打开又回来」。
2. **撤销/重做可靠**：撤销后再修改会清空重做分支；多步撤销/重做按顺序回放；类型不再允许
   在属性面板切换（避免前端改了而后端拒绝的“虚假修改”）。
3. **AI 只改你选中的页面**：原型 AI 修改必须带页面；选中组件不属于该页面时直接报错，
   不会偷偷改第一页；提案基于生成时的版本，文档被其他人改过时要求重新生成（CONFLICT）。
   当前生成方式明确标注为「本地规则生成，非模型推理」。
4. **图片不会再丢**：完整/快速备份都打包 `collab-assets` 原图，记录相对路径与 SHA-256；
   恢复到新设备/新数据目录后，数据库路径改写到当前目录，图片立即可看；文件缺失会明确报告
   并把该资产标为 `missing`，不会留下“有记录、点开报错”的假象。
5. **预览就是预览**：图片预览不再出现导入/保存/删除/缩放把手，只有编辑模式可写；
   导入上限与预览上限统一为 8 MiB，不再出现「导入成功却永远打不开」。
6. **空保存不再产生版本**：没有实际修改时保存按钮不可用；即使绕过前端，后端按内容比对
   也会拒绝写入，版本历史只记录真实变化。
