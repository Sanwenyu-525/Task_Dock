## 1. 已定决策

### D-01 保险箱使用独立数据库文件 `secure-vault.db`

| 项 | 内容 |
|---|---|
| 决定 | 数据存 `<数据目录>/secure-vault.db`，不进 `task-dock.db`；代码目录 `src-tauri/src/secure_vault/` |
| 放弃 | ① 主库加 `vault_*` 表；② SQLCipher 全库加密主库 |
| 理由 | 主库所有表强制登记 `BACKUP_TABLES`（`backup.rs:4742` 测试会 panic）→ 会被迫进明文 JSON 备份；主库 `get_settings` 全量返回；无令牌 CLI 等同 UI 权限且硬编码主库；全局搜索持主库读连接。库分离是**物理隔离**，不依赖纪律 |
| 代价 | 多一个文件、多一套迁移；跨库无法 JOIN（保险箱也不需要） |
| 推翻条件 | 主库备份改为"按表加密导出"且 CLI/搜索全部改造完成（成本更高，不建议） |

### D-03 主密码 KDF 用 Argon2id

| 项 | 内容 |
|---|---|
| 决定 | Argon2id，m=64 MiB / t=3 / p=1 / salt 16B / out 32B（基线，P1 实测定档） |
| 放弃 | PBKDF2-HMAC-SHA256（GPU 友好）、scrypt（内存参数不易跨端统一）、bcrypt（72 字节限制） |
| 理由 | RFC 9106 与 OWASP 双推荐；内存硬化抗 GPU/ASIC；RustCrypto `argon2` 成熟 |
| 代价 | 解锁需 0.5–2 s；低端机需降参数 |
| 推翻条件 | Argon2 被实质攻破，或移动端无法实现（P2 用 JCA 无 Argon2 → 见 P-02） |

### D-04 数据加密用 AES-256-GCM（而非 XChaCha20-Poly1305）

| 项 | 内容 |
|---|---|
| 决定 | AES-256-GCM + 每载荷独立 HKDF 子密钥 + 12B 随机 nonce + 显式 AAD |
| 放弃 | XChaCha20-Poly1305（nonce 更大）、XSalsa20（项目已有但为同步通道设计） |
| 理由 | **移动端可行性是决定性的**：Android JCA 原生支持 AES-GCM，不支持 XChaCha20；选 AES 可让 P2 零第三方密码学依赖。且"每条消息一把子密钥"让 96-bit nonce 的生日界风险结构性消失 |
| 代价 | 若未来出现"单密钥多消息"场景（如批量导出共用一个 key），必须改 XChaCha 或计数器 nonce |
| 推翻条件 | 需要单密钥加密 > 2^32 条消息，或 AES 被实质攻破 |

### D-05 前端拆 `src/lib/vaultBridge.ts`，由 `bridge.ts` 末尾 re-export

| 项 | 内容 |
|---|---|
| 决定 | 新增 `src/lib/vault.ts`（类型化 API）+ `vaultBridge.ts`（命令名常量）；`bridge.ts` 只加一行 re-export |
| 放弃 | 把 40+ 个函数直接塞进 `bridge.ts`（已 234 KB） |
| 理由 | `bridge.ts` 是共享枢纽（`AGENTS.md` §3.2 列为"同时写必须唯一所有者串行"），继续膨胀会让并行开发冲突概率上升 |
| 代价 | 多一个文件；调用方需要知道从 `vault.ts` 取 |
| 推翻条件 | 团队统一改为按域拆分 bridge（那时本决定自然升级） |

### D-06 每条记录拆 `meta_blob` + `secret_blob` 两级载荷

| 项 | 内容 |
|---|---|
| 决定 | 解锁时只解密全部 meta 建索引；secret 仅在打开详情/复制时按需解密 |
| 放弃 | 单 blob（解锁即解全部秘密）、每条字段单独一行（行数爆炸、无法保证同事务） |
| 理由 | 列表与搜索需要 meta；秘密长期留在内存会放大 T-06 的暴露面；两级载荷把"必须常驻内存的明文"压到最小 |
| 代价 | 每条记录 2 次 AEAD；编辑时要写两个 blob（同事务） |
| 推翻条件 | 记录数 > 2 万导致 meta 索引内存不可接受（届时改分页加载 meta） |

### D-07 明文列最小化，字段名也加密

| 项 | 内容 |
|---|---|
| 决定 | 库里只留 `id/rev/dek_ver/alg_ver/data_ver/tombstone` + nonce/ct；标题、URL、用户名、邮箱、分类、标签、时间、自定义**字段名**全在密文内 |
| 放弃 | 保留 `title`/`username` 明文列"方便列表查询" |
| 理由 | 字段名本身可能是敏感信息（如"某医院就诊卡"）；一旦有一列明文，就给了"不解锁也能画像"的能力 |
| 代价 | 列表与搜索必须解锁后从内存索引取；无法用 SQL 过滤 |
| 推翻条件 | 无（这是安全底线） |

### D-08 搜索只在内存，不建 FTS、不落缓存

| 项 | 内容 |
|---|---|
| 决定 | 解锁后遍历内存索引做 NFKC 小写子串匹配；上限 200；锁定即清；只记 `query_len_bucket` |
| 放弃 | SQLite FTS5（会把明文写进索引表）、持久化最近搜索 |
| 理由 | 现状全局搜索是查询期 `LIKE`、无 FTS（F-04）；保险箱如果自建 FTS，等于把秘密写进磁盘明文索引 |
| 代价 | 1000 条以上搜索为 O(n)，实测目标 ≤50 ms（T-PERF-04） |
| 推翻条件 | 记录数 > 2 万且实测超阈值 → 改"内存倒排 + 分片"，仍不落盘 |

### D-09 锁定默认 5 分钟闲置 / 60 秒后台，强制事件不可关

| 项 | 内容 |
|---|---|
| 决定 | 闲置 300 s、后台 60 s（可配）；锁屏/休眠/窗口隐藏/退出**强制立即**且不可配置；恢复后时钟间断 ≥10 s 也锁 |
| 放弃 | "失焦立即锁"（会让"复制→粘贴到浏览器"不可用，用户会关闭安全设置，反而更不安全）、纯前端定时器 |
| 理由 | 安全与可用性的平衡点；强制事件覆盖"用户以为关了/离开了"的真实场景；定时器必须在 Rust（前端定时器可被挂起/节流） |
| 代价 | 后台 60 s 内仍可被操作；用户可把闲置调到 30 分钟 |
| 推翻条件 | 有用户研究证明 60 s 后台过严（届时可调默认值，不取消强制事件） |

### D-10 恢复密钥 = 20B CSPRNG + HKDF（不做 Argon2）

| 项 | 内容 |
|---|---|
| 决定 | 建库生成 20 字节（160-bit）；Crockford Base32 32 字符、8 组 4 字符展示；`HKDF-SHA256` 派生 KEK_recovery；AEAD 解封装即校验 |
| 放弃 | 12 词助记词（实现复杂、易抄错）、给恢复密钥再加 Argon2（无收益）、加 checksum 字节（AEAD 已是校验） |
| 理由 | 160-bit 熵已足够抗暴力；Argon2 只对低熵输入有意义；移动端 HKDF 可用 HmacSHA256 实现 |
| 代价 | 32 字符手工抄写比 12 词长；用户可能抄错（用分组 + 粘贴 + "抄写确认"缓解） |
| 推翻条件 | 用户测试显示抄写错误率过高 → 改 24 词或分组二维码（仍需高熵） |

### D-11 备份容器 `.tdvault`：独立 `file_key` + 独立口令 + 默认无明文导出

| 项 | 内容 |
|---|---|
| 决定 | 头部明文（版本/条数/KDF 参数）+ 载荷密文；每次导出随机 `file_key`；`file_key` 由备份口令 Argon2id 派生的 KEK 封装；导入走 staging + 原子替换 + `.pre-restore` |
| 放弃 | 复用 DEK 直接加密备份、全 JSON+base64、明文 CSV 导出、把备份放 `<数据目录>/backups/` |
| 理由 | 备份文件会被复制到别处，不能成为"库的第二把钥匙"；`backups/` 会被主备份的保留策略枚举删除（`data.rs:767-822`）；staging 保证"要么成功要么原库不动" |
| 代价 | 用户需多记一个口令（默认预填主密码缓解，见 P-05） |
| 推翻条件 | 无（除非产品决定"只做整库快照"） |

### D-12 多设备用 P-256 ECDH + 设备信封，不复用配对 token

| 项 | 内容 |
|---|---|
| 决定 | 设备各自 P-256 密钥对；DEK 只以 `slot=device:<id>` 信封传输；入网需已解锁设备批准 + 6 位指纹人工比对；撤销即轮换 `dek_ver` 并重加密 |
| 放弃 | 复用 `mobile_sync` 的 `SHA-512(token)` 派生（桌面可派生 → 中继可解）、X25519（Keystore 不支持） |
| 理由 | 服务端只接触密文是硬要求；P-256 在 Android Keystore 有原生 `KeyAgreement`，私钥不可导出 |
| 代价 | P2 需写原生模块；轮换要全量重加密（N 小，可接受） |
| 推翻条件 | 若 P-02 选纯 JS 路线，则 P-256 仍在 JS 内实现（安全性下降，需重新评估） |

### D-13 Agent/MCP/CLI 采用结构性隔离，不靠"约定"

| 项 | 内容 |
|---|---|
| 决定 | `CAPABILITIES` 不新增 vault 能力位；不注册 MCP 工具；CLI 无 `vault` 子命令；REST 无端点；保险箱命令要求 `State<VaultState>`（这些入口不持有）；全局搜索不含 vault；诊断 key 闭集 |
| 放弃 | "加权限开关让用户自己开"（默认开放=迟早被打开）、"只读也允许"（读一条密码就是全部损失） |
| 理由 | 无令牌 CLI 等同 UI 全权限（F-03）；只要存在一个通用读取通道，隔离就靠人记；结构性不可达才是可验证的 |
| 代价 | P3 若要做 Agent 租约，需要新写一套租约服务（但那是显式的、可审计的） |
| 推翻条件 | 用户明确要求"Agent 可读保险箱"——即使如此也应走 P3 租约，而不是开能力位 |

## 2. 已放弃的方案（汇总）

| 方案 | 为什么放弃 |
|---|---|
| 自研加密 / Base64 / 异或 / 混淆 | 不是加密；违反 `AGENTS.md` |
| SQLCipher 整库加密 | 新依赖 + 许可；且挡不住"备份把库带走"与"CLI 读库" |
| DPAPI 作为主保护 | 绑定用户+机器，换机不可恢复；只适合做本机便捷解锁（P-08） |
| 主密码直接加密记录 | 改密码要重加密全部记录；且密码熵直接决定数据安全 |
| 单 DEK 加密全部记录（无子密钥） | nonce 复用面变大；无法按记录轮换；跨记录搬移无法检测 |
| 把 DEK 存 `application_settings` | 会进主库备份 |
| 复用同步通道密钥 | 桌面可派生，破坏服务端不可读 |
| 明文导出（默认提供） | 一键把密码扔桌面；P1 明确不做 |
| 自动填充（P1） | 需要浏览器扩展/注入，攻击面远大于收益 |
| TOTP（P1） | 身份验证器是独立产品能力，先不混入（P-04 再议） |

## 3. 待决项（需要用户拍板）

### P-01 依赖清单是否批准

| 选项 | 内容 | 利 | 弊 |
|---|---|---|---|
| A（推荐） | 新增 `argon2`、`aes-gcm`、`hkdf`、`hmac`、`base32`、`unicode-normalization`；`windows-sys` 追加 feature | 全部 RustCrypto/小型库，无 C 依赖 | 6 个新 crate 进供应链 |
| B | 只用已存在的 `zeroize`/`subtle`/`sha2`，自写 AES-GCM 与 Argon2 | 零新依赖 | **绝对不可接受**：自写密码学 |
| C | 用 `ring` 替代（含 AES-GCM/HKDF/HMAC） | 单一依赖、久经审计 | 不含 Argon2；`ring` 的 Argon2 需另找；体积更大 |

**推荐 A**。需要你回答：是否批准这 6 个 crate + 1 个 feature？
**若不定**：P1 无法开始（W1 阻塞）。

### P-02 移动端密码学实现路线

| 选项 | 利 | 弊 |
|---|---|---|
| A（推荐） | 项目内原生模块：JCA `AES/GCM` + `KeyPairGenerator(EC)` + Keystore | 私钥不可导出；零第三方密码学 | 需写原生模块（项目已有 6 个先例）；Argon2 在 Android 无原生实现 → 需纯 Java/Kotlin 实现或 JNI |
| B | `@noble/hashes` + `@noble/ciphers` 纯 JS | 实现简单、跨平台 | 私钥进 JS/SecureStore；新增依赖；Argon2 性能差 |
| C | 复用 tweetnacl（X25519/XSalsa20） | 已有依赖 | Keystore 不支持 X25519；与桌面 AES-GCM 不统一 |

**推荐 A**，但需注意：**Argon2id 在 Android 上没有系统实现**。可行做法：
① 用 `argon2` 的纯 Kotlin 实现（如 `argon2kt`，需评估许可与体积）；
② 或 JNI 编译 Rust `argon2`（与桌面同源，一致性最好，但增 NDK 构建复杂度）。
这是 P-02 的**子问题**，建议在 P2 设计评审时二选一。

**若不定**：P2 无法开始；P1 不受影响。

### P-03 默认锁定时长

| 选项 | 闲置 | 后台宽限 | 评价 |
|---|---|---|---|
| A（推荐） | 5 分钟 | 60 秒 | 安全与可用平衡 |
| B | 1 分钟 | 立即 | 更安全；复制粘贴流程痛苦，用户会关设置 |
| C | 15 分钟 | 5 分钟 | 更舒服；丢失设备风险上升 |

**推荐 A**。强制事件（锁屏/休眠/隐藏/退出）在任何选项下都立即锁定。
**若不定**：按 A 落地（可在设置里改，不算错误默认）。

### P-04 P3 是否做 TOTP

| 选项 | 利 | 弊 |
|---|---|---|
| A | 做（独立"验证器"分区） | 用户少装一个 App | 需处理时间同步、二维码解析、算法（SHA1/256/512）、迁移；且与"密码管理器"边界模糊 |
| B（推荐） | 不做，只存"恢复码" | 范围清晰、风险低 | 用户仍需别的验证器 |

**推荐 B**。若要做，必须单独立项（含 RFC 6238 实现与测试向量）。
**若不定**：按 B（不做）。

### P-05 备份导出口令是否默认预填主密码

| 选项 | 利 | 弊 |
|---|---|---|
| A（推荐） | 预填，但用户可改；必须手动确认 | 降低"忘记备份口令"的概率 | 备份安全性 = 主密码强度；改主密码后旧备份仍用旧口令 |
| B | 强制另设，不允许与主密码相同 | 密钥分离彻底 | 用户极易忘记 → 备份变废纸 |
| C | 不设口令，用恢复密钥加密备份 | 少一个秘密 | 恢复密钥泄露=备份也泄露；且恢复密钥不能解备份的"分离"原则被打破 |

**推荐 A**，并在 UI 明示"改主密码不会改变已有备份的口令"。
**若不定**：按 A。

### P-06 删除保留期

| 选项 | 保留 | 评价 |
|---|---|---|
| A（推荐） | 软删 30 天 + 回收站；彻底删除需二次确认 | 防误删；30 天足够 |
| B | 立即物理删除 | 简单；误删不可救 |
| C | 保留 1 年 | 占用小但"已删数据仍在盘上"的隐私顾虑 |

**推荐 A**。**若不定**：按 A。

### P-07 自定义分类与标签的边界

| 选项 | 规则 | 评价 |
|---|---|---|
| A（推荐） | 分类 = 互斥的"文件夹"（一条记录一个）；标签 = 多选、扁平、无层级 | 认知简单，查询清晰 |
| B | 分类也可多选 | 与标签重复，UI 混乱 |
| C | 标签支持层级（`工作/云服务`） | 表达力强，但 MVP 复杂 |

**推荐 A**；层级留到 P3 评估。**若不定**：按 A。

### P-08 P2 是否做 Windows Hello

| 选项 | 利 | 弊 |
|---|---|---|
| A（推荐，P2 可选） | 桌面解锁更快 | 需 DPAPI 绑定 + 用户在场校验；Windows Hello 只证明"本机用户"，不证明"知道主密码" |
| B | 不做，桌面只用主密码 | 简单、边界清晰 | 体验略差 |

**推荐 A 但默认关闭**：开启需用户显式设置，且**不能替代主密码**（换机/重装即失效）。
**若不定**：按 B（P2 不做）。
