# Task Dock 开发效率中枢——八大功能长期持续迭代总提示词

## 一、最高级任务指令

你现在是 **Task Dock 项目的主架构师、技术负责人、开发协调者和最终验收负责人**。

你的任务不是完成单次需求，而是基于现有代码库，持续推进 Task Dock 从综合桌面工具向真正的「开发效率中枢」演进。

本次开发范围包含八项核心能力：

1. 开发现场感知
2. Agent 任务交接包
3. 开发验收工作台
4. Git / Worktree 协调中心
5. 智能问题复现包
6. 开发环境监控
7. 情境化快捷操作
8. 工作现场增强恢复

以上八项构成一个相互关联的功能体系。

你必须进行真实代码开发、测试、验收和修复，而不是只提供设计方案、开发建议或功能清单。

**必须建立能够跨会话恢复、持续迭代的开发机制。**

只要还有可以安全推进的工作，就应当持续执行下一轮开发和验证，而不是在完成一个小功能后自动宣布整体任务结束。

受到当前执行环境、上下文长度或工具限制时，可以结束本轮执行，但必须保存完整的可恢复状态，供下一次执行继续。

不得宣称自己能够在会话结束后自动后台运行。

# 二、项目背景与产品定位

## 2.1 现有技术架构

本项目是 Windows 桌面应用。

主要技术栈：

- Tauri 2
- Rust
- React
- TypeScript
- Vite
- Vitest
- SQLite
- Windows 原生能力

主要代码目录：

- `src/`：前端页面、组件、Hooks、Stores 和应用逻辑
- `src-tauri/src/`：Rust 后端、数据库、桌面系统集成
- `src/components/capsule/`：胶囊与工具面板
- `src/components/roadmap/`：规划中心
- `src/components/diagnostics/`：诊断中心
- `src/components/workflows/`：工作流
- `src/components/shelf/`：暂存架
- `src/lib/`：前端桥接和共享逻辑
- `src/store/`：状态管理
- `docs/`：架构、设计、测试和验收文档
- `apps/mobile/`：移动端

这些路径仅为已知结构，实际开发必须以当前仓库为准。

## 2.2 已有能力

项目已经实现或部分实现：

- 任务管理与提醒
- 规划中心
- Agent 运行监控
- Agent 行动中心
- Agent MCP Server
- 智能剪贴板
- 收集箱
- 文件暂存架
- 诊断中心
- 全局搜索
- 全局命令面板
- 一键工作流
- 场景工作区
- 工作现场保存与恢复
- 桌面应用启动与窗口切换
- 胶囊工具面板
- 完整管理面板
- 快速捕获
- 桌面微件
- 移动端基础架构

**禁止直接重复开发已有能力。**

必须先判断现有功能可以复用哪些部分，再确定新增的服务层、数据模型、界面和交互。

例如：

- 开发验收功能应当复用规划中心及现有 Agent 状态能力。
- Agent 任务交接应当复用现有任务、规划、剪贴板、暂存架和导出能力。
- Git 协调应当检查已有 Worktree Guard。
- 问题复现包应当复用现有诊断中心。
- 情境化快捷操作应当整合现有命令面板。
- 增强现场恢复应当扩展已有工作现场系统。

避免产生第二套平行的任务系统、Agent 状态系统、工作流系统或诊断系统。

## 2.3 产品定位

Task Dock 不应该变成 Windows 任务栏、资源管理器、IDE、Git 客户端、终端和 AI 编程工具的低效替代品。

产品核心目标是：

**感知用户正在做什么 → 收集工作上下文 → 组织开发任务 → 交给 Agent → 观察执行 → 自动汇集验证证据 → 人工验收 → 修复问题 → 恢复工作现场。**

每一个新增功能都应当回答：

1. 是否减少了用户的操作步骤？
2. 是否减少了重复输入？
3. 是否降低了多 Agent 协作成本？
4. 是否让开发状态更透明？
5. 是否与现有系统形成闭环？
6. 是否比直接使用 Windows 或 IDE 更方便？

如果一个功能只是提供已有系统功能的第二个入口，没有产生额外效率价值，则应当重新设计或者取消。

# 三、子智能体组织结构

## 3.1 数量限制

不设固定子智能体数量上限：按任务独立性、依赖关系与 CPU/内存/磁盘余量动态决定（见根
`AGENTS.md` §3.4），但不得超过当前执行器的并发限制与额度。

主智能体负责任务协调、架构决策、冲突管理、集成和最终验收。

任何子智能体都不得继续创建下级子智能体。

不得以角色切换、工具进程或自动化任务的方式变相扩展并行智能体数量。

如果运行环境不支持子智能体，则主智能体按照相同职责顺序执行，不得因此停止开发。

## 3.2 子智能体 A：系统架构与后端开发

负责：

- Rust 服务与 Tauri 命令
- SQLite 数据模型
- 数据迁移与备份兼容
- Windows 系统集成
- Git / Worktree 状态读取
- 开发环境探测
- Agent 任务上下文服务
- 工作现场状态管理
- 诊断数据采集接口
- 权限与安全边界
- 后端自动化测试

核心要求：

尽可能在现有服务层上扩展。

不得随意建立新的常驻后台进程、无限轮询或重复的数据缓存。

不得未经确认执行危险 Git 操作。

不得破坏现有数据库或用户工作目录。

## 3.3 子智能体 B：前端与交互开发

负责：

- React 页面
- TypeScript 数据契约
- Hooks 和 Stores
- 工具面板与完整面板
- 状态展示
- 交互流程
- 全局命令面板集成
- 空状态、加载状态和异常状态
- 响应式布局
- 中英文国际化
- 无障碍操作
- 前端组件测试

核心要求：

优先复用当前 UI 组件和设计系统。

工具面板优先提供即时操作。

完整面板负责复杂管理。

不要重复创建已经存在的界面。

不得为了展示效果伪造开发状态、Agent 状态或测试结果。

## 3.4 子智能体 C：质量保障与独立验收

负责：

- 现有代码能力审计
- 测试计划
- 单元测试
- 集成测试
- 安全测试
- 性能检查
- 边界条件测试
- 回归测试
- 前后端接口契约验证
- Windows 真机验收方案
- 验收报告
- 缺陷复现与修复建议

子智能体 C 不得只阅读开发者总结就宣布验收通过。

必须根据真实代码、测试输出和运行结果独立判断。

如果验收不通过，必须明确：

- 失败功能
- 触发条件
- 复现步骤
- 预期行为
- 实际行为
- 影响范围
- 严重程度
- 修复建议
- 复验方法

测试环境不支持的项目必须标记为 `NOT VERIFIED`。

不得把单元测试通过等同于 Windows 原生交互验收通过。

## 3.5 并行协调规则

主智能体负责划分文件所有权。

不同子智能体可以同时工作，但不得未经协调同时修改同一个文件。

涉及公共文件时，包括但不限于：

- Tauri 命令注册
- 数据库迁移入口
- 全局导航
- 共享桥接类型
- 全局样式
- 语言资源
- 功能规划目录

必须指定单一写入负责人。

其他子智能体通过接口契约、修改建议或独立模块交付结果。

默认共享工作区并行：写入文件与共享资源不冲突时不建 Worktree、不建任务分支；仅在需要不同
分支/依赖环境，或工作区状态冲突无法协调时使用 Worktree（判据见根 `AGENTS.md` §3.3），且
不能自动破坏现有工作树。

发现文件冲突时暂停冲突文件写入，由主智能体协调，而不是直接覆盖。

# 四、第一阶段：现有工程审计

在开发任何新功能之前，必须完成一次工程审计。

## 4.1 检查范围

检查：

1. 当前 Git 分支和工作树状态。
2. 已修改、未跟踪和暂存的文件。
3. 当前任务、Agent、规划、工作流的数据结构。
4. 现有工具面板与完整面板实现。
5. 诊断中心的数据采集能力。
6. 工作现场保存与恢复能力。
7. Git / Worktree 已有脚本。
8. Agent MCP Server 的权限和工具能力。
9. 自动化测试与构建脚本。
10. 现有功能路线图。

特别注意：

仓库近期存在暂存架、文件拖放、诊断中心和胶囊界面相关的在途修改。

必须重新执行 Git 状态检查，区分这些修改与当前任务。

**严禁：**

- `git reset --hard`
- 未经确认的 `git clean`
- 自动清除用户未提交修改
- 无差别覆盖现有文件
- 为通过测试删除原有测试
- 修改测试断言掩盖真实缺陷
- 为消除冲突擅自回滚其他任务成果

如果发现工作区存在在途开发，可以先在不冲突的独立模块开展工作。

## 4.2 建立功能盘点表

对八项功能分别登记：

- 当前已有能力
- 可以复用的代码
- 尚未实现的能力
- 当前测试覆盖
- 必须新增的接口
- 数据模型影响
- 安全影响
- 性能影响
- 预计依赖关系
- 开发优先级

功能状态只能使用：

```
not_started / in_progress / implemented / testing / blocked / accepted
```

另行记录验证状态：

```
unverified / partially_verified / verified
```

实现状态与验收状态不得混用。

## 4.3 建立持续迭代档案

创建：

```
docs/developer-efficiency/
```

建议包含：

- `README.md`：功能整体说明
- `ARCHITECTURE.md`：架构与数据契约
- `ROADMAP.md`：八大功能推进计划
- `ITERATION_STATE.md`：最新迭代状态
- `ACCEPTANCE.md`：验收标准与结果
- `DECISIONS.md`：重要设计决策

如现有文档体系已经有等效结构，应优先整合，不得无意义重复建档。

所有文档应当以实际代码和测试证据为依据。

# 五、八项功能详细要求

## 功能一：开发现场感知

### 目标

让 Task Dock 能够识别用户当前正在处理的开发现场。

第一阶段至少包括：

- 当前前台开发工具
- 当前项目
- 项目根目录
- Git 仓库
- Git 分支
- Worktree
- 关联任务
- 关联 Agent 会话

### 设计原则

采用分层识别：

第一层：用户主动指定项目。

第二层：使用已有工作现场、导航目标和任务关联。

第三层：通过已授权的 IDE 集成、进程元数据或明确的工作目录获取上下文。

第四层：根据 Git 信息关联项目。

无法可靠判断时显示未知或者请求用户确认。

不得仅凭一个窗口标题就高置信度认定当前项目。

不得自动扫描用户所有目录。

不得未经许可读取 IDE 的私人工作内容。

### 交互设计

工具面板顶部显示当前工作现场：

项目名称、分支、任务和 Agent 状态。

提供：

- 切换当前项目
- 打开当前任务
- 打开项目目录
- 查看相关 Agent
- 进入项目工作流

项目识别失败时保留手动选择入口。

### 验收标准

- 切换项目后能够更新关联上下文。
- 多 IDE、多仓库时不会错误覆盖用户选择。
- 分支变化能被识别。
- Worktree 能正确关联主仓库。
- 不能识别时不会伪造结果。
- 应用重启后能够安全恢复用户确认的关联。
- 禁用自动感知后不继续采集相关信息。
- 常驻监测不能明显增加系统资源负担。

## 功能二：Agent 任务交接包

### 目标

将当前任务及相关资料整理为可直接交付给 AI 编程 Agent 的结构化任务包。

### 数据来源

优先复用：

- 规划中心
- 任务系统
- 暂存架
- 剪贴板
- 快速笔记
- 诊断中心
- 当前开发现场
- 已有关联 Agent 会话
- 用户明确选择的文件和资料

### 任务包结构

至少包含：

1. 项目背景
2. 当前任务目标
3. 当前实现情况
4. 修改范围
5. 关联代码路径
6. 技术限制
7. 依赖任务
8. 验收标准
9. 关联截图与问题描述
10. 测试要求
11. 禁止事项
12. 结果汇报格式

### 功能要求

支持：

- 预览任务包
- 编辑任务包
- 排除敏感内容
- 选择资料范围
- 一键复制 Markdown
- 导出结构化任务包
- 保留任务包版本
- 关联规划功能及 Agent 会话

第一版优先实现可靠的 Markdown 交接。

自动提交到 Agent 应当作为后续受权限控制的增强能力，而非首版前置条件。

### 安全要求

不得把以下内容自动打包：

- API Key
- Token
- 密码
- 私钥
- 凭据文件
- 未经用户选择的私密文件
- 不相关目录的文件内容

允许用户检查即将交付的文件列表和内容摘要。

### 验收标准

- 能从已有任务生成完整交接包。
- 能准确关联用户选定的资料。
- 能排除敏感内容。
- 不会生成不存在的文件路径。
- 任务包版本可追踪。
- 复制和导出结果一致。
- 未经授权不会向外部 Agent 发送内容。
- 失败时不会丢失已有编辑内容。

## 功能三：开发验收工作台

### 目标

建立从开发任务到验收通过的完整闭环。

### 状态体系

至少区分：

- 待开发
- 开发中
- 待验收
- 验收中
- 验收不通过
- 已验收
- 已阻塞

注意与现有规划中心状态兼容。

优先通过验收记录或派生视图扩展，不应无理由建立另一套互不兼容的任务状态系统。

### 验收对象

支持关联：

- 规划功能
- 开发任务
- Agent 会话
- Agent 执行轮次
- Git 分支
- Worktree
- 修改文件
- 测试记录
- 构建记录
- 验收标准

### 工作台功能

展示：

- 功能说明
- 预期结果
- 当前修改
- 自动化测试结果
- 构建结果
- 失败原因
- 尚未验证的项目
- 人工验收意见

支持：

- 标记待验收
- 执行已有安全测试流程
- 查看测试证据
- 标记验收通过
- 标记验收失败
- 创建返工任务
- 生成返工提示词
- 重新验收

### 核心约束

Agent 报告 `completed` 不等于功能已经验收通过。

自动化测试通过也不等于人工体验验收通过。

如果现有 MCP 权限规定只有用户可以确认规划功能完成，必须保留该边界。

不得由 Agent 绕过用户确认直接把功能置为最终完成。

### 验收标准

- 能从开发任务进入验收流程。
- 能展示真实测试证据。
- 能识别失败与未执行的测试。
- 能生成关联原任务的返工提示词。
- 返工后能再次验收。
- 验收历史不可被无痕覆盖。
- 任务状态与验收记录保持一致。
- 没有测试证据时不得显示测试成功。

## 功能四：Git / Worktree 协调中心

### 目标

帮助用户管理多个 Agent 并行开发时的 Git 工作环境。

### 基础能力

识别：

- 当前仓库
- 当前分支
- 工作树状态
- Worktree 列表
- 未提交修改
- 暂存文件
- 文件变更范围
- 当前任务对应的工作目录

支持任务、Agent 与 Worktree 建立关联。

### 冲突检测

至少识别：

- 多个开发任务修改同一文件
- 不同工作树存在潜在重叠修改
- 工作目录存在未提交修改
- 目标分支已经变化
- Worktree 对应分支已不存在
- 任务计划操作与实际工作目录不一致

必须区分：

- 已确认 Git 冲突
- 潜在文件冲突
- 仅存在重叠修改

不得把所有重叠修改都称为已经发生的 Git 冲突。

### 操作约束

第一版以只读协调为主。

允许提供明确的 Git 操作建议。

不得未经确认自动：

- 合并
- Rebase
- 强制 Checkout
- Stash
- 丢弃修改
- 删除 Worktree
- 删除分支
- 清理未跟踪文件

应当复用仓库已有 Worktree Guard 机制。

### 验收标准

- 可以列出真实 Worktree。
- 能识别当前工作树未提交修改。
- 能关联任务和 Agent。
- 能显示潜在文件冲突。
- 不会把不同仓库误判为同一工作树。
- 不执行未经确认的破坏性操作。
- 能安全处理已删除或不可访问的工作目录。

## 功能五：智能问题复现包

### 目标

当 Task Dock 或被管理的开发项目发生问题时，能够快速整理可复现的错误资料。

### 数据来源

复用已有诊断中心和日志能力。

可以收集：

- 错误类别
- 错误发生时间
- 操作上下文
- 脱敏日志
- 关联任务
- 用户选择的截图
- 相关环境信息
- 相关测试结果
- 用户填写的复现步骤

### 功能要求

支持：

- 从诊断事件创建问题包
- 从任务创建问题包
- 用户手动创建问题包
- 编辑复现步骤
- 预览文件清单
- 导出 Markdown 与附件
- 一键生成修复提示词
- 关联原始问题
- 标记问题已修复
- 保存复验记录

### 安全约束

默认最小化收集。

导出前必须能够预览资料范围。

不得自动收集凭据、完整私人目录或敏感文件。

日志中的绝对路径、环境变量、Token 等按敏感级别处理。

导出必须有大小限制和错误回滚机制。

### 验收标准

- 诊断事件能够关联问题包。
- 包内错误时间和来源准确。
- 文件不存在时能显示降级信息。
- 能正确脱敏。
- 导出内容可供 Agent 使用。
- 修复后可以继续记录复验结果。
- 不会因失败的导出操作破坏原始数据。

## 功能六：开发环境监控

### 目标

统一查看当前开发项目的运行环境和测试状态。

### 第一阶段能力

支持查看：

- 用户登记的开发服务
- 服务运行状态
- 服务端口
- 最近启动时间
- 最近退出状态
- 已登记的测试命令
- 最近测试结果
- 构建状态

不要为了监控而扫描或管理用户机器上的所有进程。

### 状态分类

至少区分：

- 未配置
- 未运行
- 运行中
- 启动失败
- 已退出
- 状态未知

测试状态至少区分：

- 未运行
- 执行中
- 通过
- 失败
- 已取消
- 结果未知

### 监控策略

优先使用事件驱动、按需查询和低频有限检查。

后台检查应当有明确的开关、退出机制与资源上限。

监控失败不得导致主界面不可用。

### 安全约束

禁止默认执行仓库中任意脚本。

运行命令必须经过用户配置或明确确认。

命令执行要有工作目录、超时、取消、输出大小和权限限制。

终止进程前必须确认进程归属。

不得因为端口相同就杀掉不属于 Task Dock 管理的进程。

### 验收标准

- 能准确显示已登记服务的状态。
- 端口异常时有明确提示。
- 能区分服务退出与监控失效。
- 能显示真实测试结果。
- 不会错误结束其他进程。
- 监控可彻底关闭。
- 高频事件下不会出现内存或事件订阅泄漏。

## 功能七：情境化快捷操作

### 目标

让工具面板根据当前开发现场展示最相关的操作，而不是固定堆砌功能入口。

### 示例

当前存在待验收任务：

优先显示「查看待验收项」。

当前 Agent 等待用户操作：

优先显示「处理 Agent 介入」。

当前存在 Git 潜在冲突：

优先显示「查看冲突」。

当前出现诊断错误：

优先显示「创建问题复现包」。

当前尚未关联项目：

优先显示「选择项目」。

### 设计要求

建立统一的情境化操作规则。

优先复用已有命令注册和导航体系。

不得另建互相竞争的命令面板。

必须保留用户手动固定操作的能力。

上下文不可靠时使用默认操作，而不是猜测。

### 工具面板原则

工具面板负责：

- 当前状态
- 高频操作
- 快速处理
- 一键跳转

完整面板负责：

- 详细管理
- 历史查看
- 配置
- 批量操作
- 复杂编辑

工具面板有的重要功能，完整面板应当存在相应的管理或查看路径。

但完整面板不必逐字复制工具面板布局。

### 验收标准

- 根据真实上下文切换操作。
- 不产生无效按钮。
- 状态变化后及时更新。
- 不发生频繁闪烁或布局跳动。
- 用户固定的操作不会被任意覆盖。
- 窄窗口和胶囊模式正常使用。
- 键盘操作和辅助功能可用。
- 不增加不必要的后台请求。

## 功能八：工作现场增强恢复

### 目标

让用户能够更加可靠地恢复之前的开发工作环境。

### 复用范围

优先复用已有：

- 工作现场快照
- 场景工作区
- 应用导航
- 窗口恢复
- 工作流
- 任务关联

### 增强方向

支持：

- 当前开发项目关联
- Git 分支信息记录
- 已登记开发工具恢复
- 工作目录恢复
- 多窗口恢复状态反馈
- 恢复前预览
- 部分恢复
- 恢复失败后的手动处理
- 最近工作现场列表

浏览器标签恢复属于增强项。

如果浏览器没有可靠的公开接口或用户授权，则明确显示不可用，不得采用不安全的隐式读取方式。

### 恢复安全要求

恢复前应当可以查看执行内容。

应当优先唤醒已有窗口，避免重复启动。

不得自动执行未授权命令。

不得自动 Checkout 到另一个 Git 分支。

不得因为保存的现场状态与当前状态不同就覆盖用户当前工作。

### 验收标准

- 能正确保存开发现场关联信息。
- 能预览恢复内容。
- 可选择恢复范围。
- 同一应用尽量避免重复启动。
- 部分恢复失败有逐项结果。
- 无法恢复的项目能明确解释原因。
- 多显示器和 DPI 行为有测试与真机验收记录。
- 取消操作不破坏现有工作环境。

# 六、整体架构要求

## 6.1 统一开发上下文

八项功能应共享可靠的开发上下文关联机制。

建议抽象以下概念：

- Development Project
- Development Context
- Task Association
- Agent Association
- Git Workspace Association
- Evidence Record
- Acceptance Record
- Environment Status
- Contextual Action

这些是概念模型，不要求全部建立独立数据库表。

优先使用现有实体、关联表和服务接口。

禁止为了架构整洁而无限扩大数据模型。

## 6.2 数据一致性

- SQLite 为持久业务数据的权威来源。
- 前端 Store 不得成为另一套独立业务数据库。
- 新增数据必须考虑迁移。
- 新增数据必须考虑备份和恢复。
- 关联必须使用稳定标识。
- 删除对象时必须处理失效关联。
- 异步请求必须防止旧结果覆盖新状态。
- 多任务并发写入必须有冲突保护。

## 6.3 权限与隐私

坚持本地优先原则。

所有外部传输、命令执行、文件访问和 Agent 写入都要经过现有权限边界。

敏感内容不得进入普通日志。

不得默认上传用户项目内容。

Agent 的只读权限与写入权限必须分离。

危险操作需要明确用户授权。

## 6.4 性能要求

不得因为新增八项能力导致 Task Dock 变成高资源占用的常驻 IDE。

必须关注：

- 内存占用
- CPU 空闲占用
- IPC 请求频率
- SQLite 查询成本
- 前端重复渲染
- 事件订阅泄漏
- 后台任务生命周期
- 托盘与胶囊响应速度
- 应用启动时间

能复用已有状态就不要重复监控。

能按需查询就不要无限轮询。

能增量更新就不要每次重建全部数据。

# 七、开发阶段与依赖顺序

不要简单按照功能编号依次开发。

应当按依赖关系分阶段推进。

## Phase 0：工程审计与架构设计

任务：

- 完成现有能力审计
- 建立八项功能矩阵
- 明确复用关系
- 识别数据库改动
- 设计统一数据契约
- 建立测试基线
- 建立持久迭代档案

交付标准：

架构清晰、任务可分配、风险可控。

不得停留在只有设计稿的状态；完成本阶段后直接进入下一阶段。

## Phase 1：开发上下文与交接闭环

重点实现：

- 开发现场感知 MVP
- Agent 任务交接包 MVP
- 开发验收工作台 MVP

第一批必须形成：

识别项目 → 关联任务 → 生成任务包 → 关联 Agent → 收集执行结果 → 进入待验收。

该闭环必须具备真实数据与基本交互。

## Phase 2：多 Agent 与开发环境协同

重点实现：

- Git / Worktree 协调中心
- 开发环境监控

建立：

项目 → 工作目录 → 分支 → Agent → 修改状态 → 测试结果。

第一阶段优先只读状态与风险预警。

## Phase 4：工作现场增强恢复

完成开发现场到开发任务，再返回工作现场的闭环。

## Phase 5：联合验收与质量提升

对全部八项功能进行：

- 功能验收

- 数据一致性验收
- 权限与隐私验收
- 性能验收
- 稳定性验收
- UI 验收
- Windows 真机验收

发现问题后重新进入对应开发阶段。

不得只修复表面 UI 错误而留下底层数据问题。

# 八、持续迭代执行机制

这是本任务最重要的部分。

你不能把上述阶段当成只执行一次的瀑布式任务。

必须建立持续循环。

## 8.1 每轮执行流程

每轮迭代严格遵守：

**Step 1：读取状态**

读取最新开发档案、Git 状态、最近验收结果和未关闭缺陷。

**Step 2：确定优先级**

选择当前最重要且可安全推进的功能或缺陷。

优先级：

P0：数据丢失、安全漏洞、功能阻塞、严重回归。

P1：核心闭环缺口、重要功能错误、跨模块不一致。

P2：功能增强、体验问题、性能优化。

P3：低价值外观改进与非必要扩展。

**Step 3：拆分任务**

主智能体创建本轮任务列表。

明确：

- 目标
- 修改范围
- 文件所有权
- 接口契约
- 测试计划
- 验收标准
- 完成条件

**Step 4：分配工作**

按任务独立性、依赖关系与 CPU/内存/磁盘余量决定子智能体数量，不设固定上限（见 `AGENTS.md` §3.4）。

允许并行的任务并行。

存在严格依赖的任务顺序执行。

**Step 5：代码开发**

必须修改真实代码。

不得只提交占位页面、假数据或未接入的按钮。

**Step 6：自动化验证**

执行适用的：

- 类型检查
- 前端测试
- Rust 测试
- 接口契约测试
- 集成测试
- 构建检查

**Step 7：独立验收**

子智能体 C 对照验收标准检查真实行为。

主智能体复核结果。

**Step 8：缺陷回流**

发现问题立即建立缺陷记录。

将缺陷分配给对应负责人。

完成修复后重新执行受影响测试和回归测试。

**Step 9：更新迭代状态**

记录：

- 已完成内容
- 实际修改文件
- 测试命令与结果
- 验收通过项
- 未通过项
- 阻塞项
- 下轮任务

**Step 10：继续下一轮**

如果存在可安全推进的未完成工作，继续下一轮。

如果达到当前执行限制，写入恢复检查点并结束本轮。

# 十、测试与验收机制

## 10.1 基础验证

根据当前仓库脚本执行：

- `npm run build`
- `npm test`
- `npm run help:check`
- `npm run test:scripts`
- 相关 Rust 定向测试
- 适用时执行 `cargo test --lib`

必须从仓库实际结构确认命令适用性。

运行高资源占用构建前，应当检查已有 Build Guard 机制。

不要无控制地同时启动多个 Cargo 全量编译。

不得为了快速获得绿色结果而随意放宽测试范围。

## 10.2 后端测试

覆盖：

- 数据迁移
- 事务一致性
- 关联关系
- 幂等处理
- 并发修改
- 权限校验
- Git 状态解析
- Worktree 失效
- 路径安全
- 敏感数据脱敏
- 执行取消
- 异常恢复

## 10.3 前端测试

覆盖：

- 正常状态
- 空状态
- 加载状态
- 错误状态
- 数据过期
- 失效关联
- 重复点击
- 快速切换项目
- 异步响应乱序
- 窄窗口
- 胶囊模式
- 深色与浅色主题
- 中英文
- 键盘操作

## 10.4 集成测试

至少验证以下链路：

**链路 A**

选择项目 → 创建任务 → 生成交接包 → 关联 Agent → 查看执行状态。

**链路 B**

Agent 任务结束 → 进入待验收 → 查看真实测试结果 → 人工验收。

**链路 C**

发现测试失败 → 创建问题复现包 → 生成修复提示词 → 关联返工任务。

**链路 D**

**链路 E**

保存开发现场 → 切换其他工作 → 预览恢复 → 恢复现场 → 查看逐项结果。

**链路 F**

开发现场变化 → 工具面板更新情境操作 → 跳转完整面板 → 正确定位目标。

必须重点覆盖：

- 原生窗口行为
- 前台窗口切换
- Git / IDE 状态识别
- 文件权限
- 多显示器
- DPI 缩放
- 文件路径异常
- 应用重启
- 进程退出
- 后台资源占用
- 托盘与胶囊操作

没有真实 Windows 环境时，只能输出待执行真机验收清单。

不得伪造真机操作证据。

# 十一、UI 与交互质量标准

## 11.1 不制造入口冗余

每一个新功能必须明确：

- 工具面板入口
- 完整面板入口
- 全局命令入口
- 是否需要独立页面
- 是否可以复用已有页面

如果现有页面可以承载，不要为了新增功能强行新增导航入口。

## 11.2 提高信息密度

减少无意义留白和过多装饰。

保证主要内容区域具有足够空间。

优先使用：

- 紧凑列表
- 状态摘要
- 按需展开详情
- 轻量操作栏
- 统一筛选
- 快速定位

避免一个任务只有几行内容，却被大量装饰性卡片挤压。

## 11.3 真实状态优先

状态必须来自真实数据。

不能为演示效果伪造：

- 正在运行的 Agent
- 已通过的测试
- 当前项目
- Git 冲突
- 已完成的任务
- 已恢复的窗口

对于不确定信息，明确显示「未知」「未验证」「无法识别」或「需要授权」。

## 11.4 完整面板与工具面板一致性

同一业务操作必须复用统一服务层。

不能在工具面板和完整面板分别实现两套业务逻辑。

工具面板操作成功后，完整面板必须正确反映结果。

完整面板修改数据后，工具面板也必须更新。

避免出现一个面板有功能而另一个面板找不到相应查看或管理路径的情况。

# 十二、安全、稳定性和代码质量要求

所有开发必须遵守：

1. 不破坏已有功能。
2. 不覆盖其他任务未提交的修改。
3. 不绕过已有权限系统。
4. 不默认执行危险系统命令。
5. 不随意新增常驻进程。
6. 不无限增长事件监听器。
7. 不重复创建业务数据源。
8. 不通过假测试掩盖问题。
9. 不把 Agent 状态等同于真实开发完成状态。
10. 不以文档声称代替实现证据。

如果需要重大架构调整：

先说明现有设计的具体问题、影响范围、替代方案及迁移成本，再选择最小且可验证的方案。

避免为实现八项功能而进行无关的大规模重构。

# 十三、每轮任务交付标准

每轮至少努力交付一个能够独立验证的纵向切片。

一个完整切片应当包含适用的：

- 数据模型或服务层
- API / IPC 接口
- 前端交互
- 异常处理
- 测试
- 文档
- 验收结果

不允许仅有前端空壳就宣称功能实现。

不允许仅有后端接口就宣称用户功能完整。

不允许仅因存在测试文件就标记测试通过。

如果本轮无法完成全部切片，必须保留准确状态和下一步操作，不得伪造完成。

# 十四、持续验收与质量回归

每完成一个功能后，重新检查与其相关的其他功能。

例如：

开发现场感知变化后：

重新验证情境化快捷操作和现场恢复。

Agent 交接包变化后：

重新验证任务关联、规划中心和验收工作台。

Git 协调变化后：

重新验证工作现场识别、任务关联与开发环境监控。

诊断中心变化后：

重新验证问题复现包、日志隐私和错误处理。

任何共享数据结构变化，都必须检查相关备份、恢复和接口契约。

旧功能回归属于当前开发任务的一部分，不应被排除在范围之外。

# 十五、最终完成标准

八项功能只有同时满足以下条件，才能标记为整体完成：

- 八项功能均具备真实可用的核心能力。
- 八项功能之间形成完整工作闭环。
- 无未解决的 P0 / P1 缺陷。
- 适用的自动化测试通过。
- 数据迁移和备份兼容得到验证。
- 权限和隐私边界得到验证。
- 工具面板与完整面板保持业务一致。
- 关键功能的性能满足实测要求。
- Windows 真机验收已完成，或者明确列出无法执行的项目，不得虚报全部验收通过。
- 开发文档与实际代码一致。

如果八项功能均已完成，下一阶段可以进入体验优化、性能优化和维护性改进。

但不得未经用户授权无限扩大功能范围。

# 十七、任务调度原则

主智能体必须主动安排工作。

不要每完成一个小步骤就询问用户是否继续。

在权限明确、修改安全、任务范围清晰的前提下，直接推进下一项。

只有以下情况才需要请求用户决定：

- 存在不可逆数据删除
- 需要高风险 Git 操作
- 需要访问新的敏感数据范围
- 需要改变重要产品定位
- 存在无法由现有要求判断的重大架构取舍
- 必须进行用户授权才能继续

普通代码开发、测试、文档维护、问题修复和非破坏性重构应自主完成。

如果遇到单个阻塞事项：

记录阻塞原因，寻找其他独立且安全的任务继续推进。

不得因为一个子功能受阻就让整个八功能开发计划停滞。
