# 后台同步设计评估（前台自动 / 仅 Wi-Fi / 后台任务）

> 状态：**仅设计，未实现**（2026-11-12）。本文不改变任何现有行为；按任务约束，本轮
> **未启用任何新的自动网络行为**，也未改动 `src/lib/sync/engine.ts`（该文件归同步安全
> 任务所有）。实施前需与 `docs/mobile/07-sync.md` 的契约复核。

## 1. 现状基线

- 同步是**手动触发**：同步页「立即同步」→ pull → push → 再 pull（07-sync.md §1/§4）。
- 传输：局域网 `http://<桌面IP>:47822`（清单级 usesCleartextTraffic），载荷 XSalsa20-Poly1305
  加密；配对令牌存 SecureStore。
- 失败处理：客户端 5s 超时 + 退避重试；无后台轮询。
- 已知厂商约束：vivo Funtouch 后台策略激进（提醒不投递已有实证，04-testing §6），
  对「后台同步」的存活率预期必须按同样口径打折。

## 2. 方案 A：前台恢复自动同步（建议第一步）

**行为**：App 回到前台（AppState active）且距上次成功同步 ≥ 阈值（建议 5 分钟）且已配对时，
静默执行一次手动同价的 pull→push→pull；失败静默（Toast 可选），不打断用户操作。

- **实现面**：纯 JS。`App.tsx` 已有 AppState→version 通道；在同步域加一个
  「上次成功同步时间」（kv）+ 单飞互斥（与手动同步共用 engine 的既有单飞/超时/退避，
  不改 outbox 契约）。预估 1-2 天含真机回归。
- **依赖**：B 的 TLS/协议 v2 落地后再启用（自动行为建立在更安全的传输上）；
  冲突页弹出策略需定义（自动同步遇冲突：只标记不强制弹页）。
- **风险**：
  - 蜂窝网络意外流量（由方案 B 的开关兜底）；
  - 自动失败静默化后用户无感 → 需在同步页保留「上次同步时间/结果」；
  - 与桌面端 `http_ingest` 并发上限（127.0.0.1 单监听、单客户端假设）——自动同步不改变
    并发模型，只是频率变高。
- **成本评级**：低。

## 3. 方案 B：仅 Wi-Fi 同步开关（与 A 组合交付）

**行为**：kv 开关 `wifi_only_sync`（默认开）。A 的自动同步触发前检查网络是否非计费
（Wi-Fi）；手动「立即同步」不受限（用户显式动作），但可在结果里提示当前是计费网络。

- **实现面**：需要知道网络类型 → Expo SDK 58 无内置 API，两个路径：
  1. 本地 Expo module（如 `modules/network-state/`）读 `ConnectivityManager` +
     `NetworkCapabilities.NET_CAPABILITY_NOT_METERED`：零新依赖，~80 行 Kotlin + JS 封装，
     与 share-intent 同模式。**推荐**。
  2. `expo-network`（官方小包）：引入新依赖，违反 apps/mobile 的「不新增依赖」默认红线，
     除非用户批准。
  预估 A+B 合计 2-3 天含真机回归（含 Wi-Fi/蜂窝切换用例）。
- **依赖**：方案 A 先行；无桌面端改动。
- **风险**：
  - VPN/以太网共享下 `NOT_METERED` 判定与用户直觉有偏差 → 开关语义写清「非计费网络」；
  - 判定不可用时 fail-closed（视为计费网络，不做自动同步）；
  - UI 需解释「为什么没有自动同步」（同步页显示当前网络与开关状态）。
- **成本评级**：中。

## 4. 方案 C：后台同步（建议最后，条件触发再评估）

**行为**：App 不在前台时也能周期性 pull/push。

- **实现面**（三选一）：
  1. `expo-background-task` / `expo-task-manager`（官方，SDK 58 提供 background task API）：
     依赖 expo-background-task + expo-network 两个新包；JS 回调在受控窗口内跑同步。
  2. 自建 WorkManager 本地 module + headless JS：同步逻辑在 TS，headless 启动 RN 上下文
     的内存/时延成本高，等于把整条同步管线拖进后台执行环境，工程量最大。
  3. 把同步下沉为 Kotlin 原生实现：与「同步逻辑在 TS/与桌面端契约对齐」的现状冲突，
     双实现漂移风险，不建议。
- **依赖**：A、B 先行（复用同一单飞与开关语义）；桌面端 TLS（B 在做）；厂商电池优化
  白名单引导 UI。
- **风险**：
  - vivo/华为后台存活率低（已有提醒不投递实证）→ 收益可能远小于成本；
  - 后台窗口内 SecureStore 解锁态、SQLite WAL 并发、与前台同步的互斥都要重新论证；
  - 自动网络行为的隐私/流量告知义务。
- **成本评级**：高（官方包路径约 1 周 + 真机矩阵；headless 路径 2-3 周）。
- **建议**：先上 A+B 观察实际「前台错过同步」的频率，再决定是否投入 C；
  若 C 落地，优先 expo-background-task 路径并接受「尽力而为」语义。

## 5. 建议顺序与验收要点

1. **A 前台自动同步**（TLS 落地后）：验收——真机隔网切换、失败静默、单飞不重入、
   与手动同步互不踩踏、桌面端 sync_changes 无异常膨胀。
2. **B 仅 Wi-Fi 开关**：验收——Wi-Fi 自动 / 蜂窝不自动 / 开关关闭不自动 / 手动始终可用，
   判定 fail-closed。
3. **C 后台同步**：条件触发（A/B 数据支持 + TLS 完成），先在 vivo 真机测存活率再排期。

共同红线：任何方案都不得绕过 `engine.ts` 的单飞/超时/退避与 outbox 同事务契约；
自动同步失败不得清空用户数据、不得把可重试错误当致命错误；全部开关默认保守
（默认不自动 / 默认仅非计费网络）。
