# 设计模式使用规范（DESIGN PATTERNS）

| 项目 | 内容 |
|---|---|
| 文档状态 | 生效（Phase 1，待评审） |
| 最后更新 | 2026-11-19 |
| 适用范围 | 全项目（桌面前端 / Rust 后端 / 移动端） |

## 决策矩阵总览

| 模式 | 结论 | 主要适用点 |
|---|---|---|
| Repository | ✅ 采用 | SQLite、文件元数据、任务/剪贴板/工作区/移动本地数据 |
| Unit of Work | ✅ 采用 | 多表写入、跨实体事务、备份恢复 |
| Strategy | ✅ 采用 | Agent Provider、文件操作、平台适配、同步策略 |
| Adapter | ✅ 采用 | Tauri、Win32、外部 Agent/MCP/CLI、跨端通信 |
| Registry | ✅ 复用已有 | Feature、Provider、插件、工具、命令、导航、工作流节点 |
| State Machine | ✅ 采用 | 文件操作、配对、投屏、工作流、Agent、备份、同步、启动 |
| Observer/Event | ⚠ 受限采用 | 跨模块通知（有类型/版本/释放，禁全局 EventBus） |
| Command | ⚠ 评估采用 | 文件删除/移动/复制/恢复的可追踪操作对象 |
| Decorator | ⚠ 采用（横切） | 日志、性能、错误归一化、超时、重试 |
| CQRS | ❌ 拒绝（当前） | 仅统计聚合未来可评估，不为 CRUD 造读写模型 |
| Outbox | ✅ 已是事实 | 移动同步（已实现），桌面侧评估 |

## 1. Repository ✅

- **问题**：UI/业务直接写 SQL，数据访问散落（SQL 热点 273/190/170/108/98 处）。
- **不用会怎样**：SQL 变更波及全项目，无法独立测试数据访问，Domain 被存储细节污染。
- **增加的复杂度**：多一层 trait + 实现。
- **更简单方案**：对单表简单 CRUD，直接 Db 闭包即可——允许，不强制 Repository。
- **适合栈**：Rust trait 天然适合；TS 侧用接口 + 实现。
- **测试**：trait 契约测试（同一行为集），实现可替换内存版。
- **扩展**：新存储引擎只需新实现。

## 2. Unit of Work ✅

- **问题**：多表写入部分提交导致数据不一致。
- **不用会怎样**：备份/恢复、任务关联更新、Outbox 写入可能半途失败。
- **复杂度**：事务边界需显式管理。
- **更简单方案**：单表写入用单事务即可，不必引入 UoW 对象。
- **栈**：Rust `with_transaction()` 已具备；移动端 `withTransactionAsync` 已具备。
- **测试**：注入失败验证回滚，验证 `user_version` 不推进。
- **扩展**：跨领域事务经 Application Service 编排。

## 3. Strategy ✅

- **问题**：Agent Provider、平台、同步策略用大量 if/else 选择实现。
- **不用会怎样**：新增 Provider 改多处条件分支。
- **复杂度**：策略接口需保持稳定。
- **更简单方案**：只有 1–2 个分支时不抽象。
- **栈**：Rust trait object / 泛型；TS 接口 + 工厂。
- **测试**：每个策略独立单测；策略切换集成测试。
- **扩展**：新增实现不改调用方（已有 Adapter 雏形）。

## 4. Adapter ✅

- **问题**：Tauri/Win32/外部 Agent/MCP/CLI/移动协议变化会污染业务领域。
- **不用会怎样**：业务代码直接依赖外部 API，无法测试、无法替换。
- **复杂度**：多一层转换。
- **更简单方案**：无——外部边界必须隔离。
- **栈**：Rust trait + 平台模块；TS platform/ 目录。
- **测试**：Adapter mock 测试，契约测试。
- **注意**：不把所有 Tauri API 塞进一个巨大适配器；窗口行为等 UI 直连属合理例外（见 FRONTEND_ARCHITECTURE.md §3）。

## 5. Registry ✅（复用已有）

- **问题**：Feature、导航、插件、工具、命令入口需要集中登记与按需加载。
- **不用会怎样**：入口散落，按需加载与生命周期无法统一管理。
- **复杂度**：需维护注册表与加载器。
- **更简单方案**：无——已有 `featureRegistry.ts`/`featureRuntime.ts` 成熟，直接复用理念。
- **栈**：TS 注册表 + 静态字面量 import。
- **测试**：`registry.test.ts` 锁定约束（preload 数量、instance 策略）。
- **扩展**：新功能在 registry 登记即可；治理"多套注册表命名混淆"问题（见审计 P2-20）。

## 6. State Machine ✅

- **问题**：文件操作、配对、投屏、工作流、Agent 执行、备份恢复、同步、启动涉及复杂状态，当前大量用 Boolean 拼接。
- **不用会怎样**：非法状态转换、超时/取消/失败处理遗漏、资源泄漏。
- **复杂度**：状态与转换表需显式定义。
- **更简单方案**：少于 3 个状态且无异步时用布尔即可，否则上状态机。
- **栈**：Rust enum + match；TS 判别联合类型 + reducer。
- **必须明确**：状态、合法转换、进入/退出动作、超时、失败、重试、取消、资源释放。
- **测试**：状态转换覆盖（合法/非法）、超时/取消/失败路径。

## 7. Observer/Event ⚠（受限）

- **问题**：跨模块一对多通知需要解耦。
- **不用会怎样**：发布方需知道所有订阅方。
- **复杂度**：事件有类型/版本/释放/节流/循环检测成本。
- **更简单方案**：直接接口调用（优先）——只有一对多且发布方不应知道订阅方时才用事件。
- **栈**：Tauri listen/emit；TS 统一 subscribeEvent 封装。
- **红线**：禁全局 EventBus；事件有版本；监听器有释放；高频合并；禁事件循环。
- **测试**：订阅清理、无循环、版本兼容。

## 8. Command ⚠（评估采用）

- **问题**：文件删除/移动/复制/恢复等操作需要可追踪、可撤销、长时运行。
- **不用会怎样**：操作状态散落，无法统一取消/进度/幂等。
- **复杂度**：命令对象 = 额外抽象层。
- **更简单方案**：一次性简单操作用普通函数即可。
- **栈**：Rust 命令对象 + 操作 ID；TS service + AbortSignal。
- **决策**：**渐进采用**——仅在文件操作域（已有 `operationQueue`/`fileJobs` 雏形）规范化为可追踪命令对象，不推广到普通 CRUD。
- **测试**：幂等性、取消、进度、失败回滚。

## 9. Decorator ⚠（横切）

- **问题**：日志、性能统计、错误归一化、超时、重试在每个业务方法重复。
- **不用会怎样**：横切逻辑散落、不一致。
- **复杂度**：装饰器链增加调用栈深度。
- **更简单方案**：少量方法直接写即可；成规模才抽横切。
- **栈**：Rust 中间件/包装函数；TS 高阶函数/wrapper。
- **决策**：采用为**统一横切工具**（如 `withErrorNormalization`、`withTimeout`、`withRetry`），不深入业务方法内部。
- **测试**：横切行为单测（超时触发、重试次数、错误映射）。

## 10. CQRS ❌（拒绝，当前）

- **问题**：读写模型混用导致复杂查询影响写入。
- **不使用缺陷**：当前无证据表明读写冲突到需要分离。
- **复杂度**：读写模型分裂、最终一致性成本。
- **更简单方案**：普通 CRUD 用同一模型；统计查询加索引/物化视图即可。
- **决策**：**拒绝**。仅当任务统计、文件统计、Agent 运行历史、工作流统计、仪表盘聚合出现明确的读写性能冲突时，再单独评估（写 ADR），不为用 CQRS 而拆每个 CRUD。

## 11. Outbox ✅（已是事实）

- **问题**：本地数据写入与待同步事件的一致性。
- **现状**：移动端已实现 Outbox 表（`op_id/entity/target_id/base_rev/payload` + 重试列 + 三态补丁），业务表与 outbox 同事务写入。
- **复杂度**：需结算与清理机制。
- **更简单方案**：无——跨设备同步必须有一致性保证。
- **栈**：SQLite 事务（已具备）。
- **决策**：保持并文档化；桌面侧若有本地待同步事件，评估复用同一模式。
- **测试**：写入-同步-结算一致性、冲突处理、离线重试。

## 12. 模式使用决策模板（新增模式时填写）

每个新引入的模式必须回答：
1. 当前存在什么问题？2. 不用有什么缺陷？3. 用了增加什么复杂度？4. 有无更简单方案？5. 适合 Rust/TS 当前栈吗？6. 如何测试？7. 未来如何扩展？

不合理的模式使用必须明确拒绝并记录理由（参见 CQRS 条目）。
