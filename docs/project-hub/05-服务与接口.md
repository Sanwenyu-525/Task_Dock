# 项目中枢：服务与接口设计

> 版本：2026-11-18 设计基线
> 目标：把「项目 / 计划 / 能力 / 任务 / 工作空间 / 进度 / 资源」拆成职责清晰的 8 个服务，
> 禁止堆进一个巨型 `ProjectService`；同一业务事实只有一个写入口。
> 实现状态：`src/lib/projectHub/` 已落地纯领域逻辑（目标/草案/修订/进度/能力/任务/工作空间/
> 资源/总览，9 文件 114 用例）；Rust 服务与 IPC 为待实施。

## 2. 共享类型（摘要）

```ts
type ProjectKind = "development" | "game" | "ai_comic" | "general" | "novel";
type ProjectLifecycle = "active" | "archived";
type PlanStatus = "planning" | "in_progress" | "paused" | "completed";
type Necessity = "required" | "recommended" | "optional";
type Mastery = "expert" | "proficient" | "basic" | "learning" | "none" | "unknown";
type ResourceAvailability = "available" | "partial" | "unavailable" | "unknown";
type FieldSource = "user" | "template" | "inferred" | "default";

interface ProgressMetric {
  completed: number;
  total: number;
  percent: number | null;       // total=0 → null，禁止显示 0%
  source: "tasks" | "phases" | "milestones" | "overall";
  note?: string;
}

interface ProgressSnapshot {
  tasks: ProgressMetric;
  phases: ProgressMetric;
  milestones: ProgressMetric;
  overall: ProgressMetric;      // 阶段等权；无阶段回退任务并标注
  computedAt: string;
}

interface CapabilityLine {
  capabilityId: string;
  name: string;
  category: "human" | "tool" | "ai" | "agent" | "external";
  necessity: Necessity;
  phaseId: string | null;
  mastery: Mastery;             // 未知 = unknown
  resource: ResourceAvailability;
  impact: string;
  alternative: string;
}

interface CapabilityStatus {
  masteryScore: number | null;      // 仅统计已评估
  resourceScore: number | null;
  assessedRequired: number;         // 已评估的必需能力数
  unassessedRequired: number;       // 未评估的必需能力数
  label: "ready" | "partial" | "blocked" | "unassessed";
  lines: CapabilityLine[];
  computedAt: string;
}

interface ProjectOverview {
  project: ProjectSummary;
  goal: string;
  currentPhase: PhaseSummary | null;
  progress: ProgressSnapshot;
  capability: CapabilityStatus;
  risks: ProjectRisk[];             // ≤3 展示，完整列表另取
  nextActions: NextAction[];        // ≤3
  recentDeliverables: DeliverableSummary[];
  recentEvents: ProjectEvent[];
  computedAt: string;
  stale: boolean;
}
```

## 3. 服务职责与方法

### 3.1 ProjectService（项目根）

| 方法 | 输入 | 输出 | 说明 |
|---|---|---|---|
| `createProject` | `ProjectCreateInput`（名称/kind/描述/目标/日期/根目录） | `ProjectSummary` | 单事务：项目 + 默认计划；不生成阶段（除非带模板） |
| `updateProject` / `update_project_fields_tx` | `projectId` + `ProjectRootPatch` | `ProjectSummary` | **第五轮收紧**：`ProjectRootPatch{name,kind,description,goal,lifecycleStatus(active\|archived),targetDate,expectedProjectRevision}`；`expectedProjectRevision` **必填**（缺失 Validation）；同事务「读→比对→根 revision+1」+ 计划镜像同步；冲突 `Conflict`；镜像写不动计划 revision；空补丁（只有令牌）→ Validation，不推进 revision |
| `updatePlan` / `update_plan_tx`（`commands::planning`） | `planId` + `PlanPatch` | `PlanningProject` | 只改执行状态/排序；**不接受** name/description/targetDate；`expectedPlanRevision` 必填；空补丁 Validation；只推进计划 revision |
| `updateProjectAndPlan`（组合用例） | `planId` + `ProjectRootPatch` + `PlanPatch` | `{project, plan}` | 同一事务校验两个 revision → 改根 → 同步镜像 → 改计划字段；任一冲突整体回滚 |

> **revision 事实源（v93）**：项目根并发令牌 = `workspace_projects.revision` 列（迁移 v93，
> DEFAULT 1）；`ProjectSummary.revision` 与 agent_access 读模型同源（该列），与计划
> `planning_projects.revision`（v37）互相独立。乐观并发校验唯一实现
> `project_hub::service::check_expected_revision_tx`（计划行与根行共用）。
| `deleteProject` | `id` | `Ok` | 先 integrity 校验；级联规则见数据模型 §4 |
| `getProject` | `id` | `ProjectSummary` | 不存在返回 `NotFound` |
| `getProjects` | `filter`（kind/status/搜索/分页） | `Page<ProjectSummary>` | 默认 50，最大 200 |
| `getProjectOverview` | `id` | `ProjectOverview` | 聚合读模型；单次批量查询；60s 缓存 |
| `validateProjectIntegrity` | `id` | `IntegrityReport` | 阻塞/警告分级；不自动修复 |

## 5. 错误模型

| 错误码 | 场景 | 前端行为 |
|---|---|---|
| `project_not_found` | 项目不存在/已删 | 清空当前项目，回到列表 |
| `project_conflict` | revision 不匹配 | 提示刷新，保留用户输入 |
| `integrity_blocked` | 校验阻塞 | 展示问题清单，不执行删除/应用 |
| `revision_invalid` | 修订引用不存在/越界 | 展示具体字段，草案不落库 |
| `capability_in_use` | 删除被引用能力 | 展示引用项目/任务数 |
| `resource_unavailable` | 目标离线 | 标注不可用，不阻断保存 |
| `draft_invalid` | 结构校验失败 | 逐段标记，保留原文 |
| `ai_unavailable` | AI 端口不可用 | 提供本地/手动降级 |
| `forbidden_scope` | 跨项目/跨作用域写 | 拒绝并记录 |
| `internal` | 其他 | 原样可读错误，不伪造成功 |

规则：错误必须可读、可定位；禁止 `Err("")`；禁止把失败包装成成功空数据。

## 6. 幂等、事务与性能

| 项 | 规则 |
|---|---|
| 幂等 | 能力需求/资源关联/任务关联用唯一键 upsert；重复 apply 同一 revision 返回已应用结果 |
| 事务 | 创建项目、应用修订、回滚、删除项目：单事务；跨域读不开启写事务 |
| 查询 | `getProjectOverview` 一次批量查询（项目/计划/阶段/任务计数/能力/交付物/事件），禁止逐项 N+1 |
| 缓存 | 读模型 60s 内存缓存，键 `projectId + revision + 相关表版本`；切项目失效 |
| 事件 | 任务状态变更只触发受影响项目重算；不监听目录、不轮询 |
| 取消 | 解析/生成/修订接受 `AbortSignal`；Rust 端超时与取消令牌 |
| 上限 | 概览事件 30 条；风险 10 条；下一步 5 条；能力明细 200 条 |
| 静默失败 | 不允许；降级必须返回 `degraded` 标记与原因 |

## 7. 与既有命令的关系（避免第二套写路径）

| 既有命令 | 迁移后行为 |
|---|---|
| `planning_create_project` | 内部：`ProjectService::createProject` + `PlanningService::createProjectPlan`；返回计划实体（签名不变） |
| `planning_update_project_root` / `planning_update_plan` / `planning_update_project_and_plan` | 第五轮起替代 `planning_update_project`：根字段与计划字段分别写入，各自携带 revision；组合命令同事务 |
| `planning_delete_project` | 内部 `deleteProject(projectId)`（删除整个项目，不只是计划）——**Breaking**：需在文档与 UI 明示 |
| `planning_*_feature/milestone/step` | 内部计划服务；不改签名 |
| `workspace_project_*` | 保持；新增读模型命令，不改变写入 |
| `mcp` 规划工具 | 授权按**项目根**（计划 ID 入参先解析为根）；写路径经项目根/计划两个服务，返回结构不变 |

> `planning_delete_project` 的语义变化是本次唯一有用户可见影响的兼容点：原「删除规划项目」
> 现在等于「删除整个项目（含工作空间登记）」。实施时必须：确认文案列出工作空间与任务影响；
> 提供「只删计划、保留项目」的新命令；旧命令在删除前要求 `confirmed=true`。
> 在未实施前，文档与代码均保持旧行为。

### 7.1 实施更正（2026-11-20）

上文「`planning_delete_project` = 删除整个项目」**未采用**。实际实现遵循「旧命令不得直接删除项目根」
与「不得静默删除最后一个有效计划」两条硬约束：

| 既有命令 | 实际行为（2026-11-20 起） |
|---|---|
| `planning_create_project` | 单事务创建 `workspace_projects` 项目根 + `planning_projects` 初始计划（`is_active=1`、回填 `workspace_project_id`、项目 `active_plan_id`）；返回计划实体，签名不变 |
| `planning_update_project_root`（第五轮替代 `planning_update_project`） | 只写项目根字段（名称/描述/目标日期/生命周期），携带 `expected_project_revision`；同事务同步计划镜像列，不推进计划 revision；返回 `{project, plan}` |
| `planning_update_plan` | 只写计划执行状态/排序，携带 `expected_plan_revision`；不碰项目根与镜像列 |
| `planning_update_project_and_plan` | 两个聚合同一事务写；任一 revision 冲突整体回滚 |
| `planning_archive_project` | 只改计划 `archived`，**不改项目根 status**；项目归档走 `workspace_project_set_status` / `ProjectService::archive_project` |
| `planning_delete_project` | 只删除计划及其功能/步骤/里程碑/历史；**项目根保留**。若它是项目最后一个计划 → 返回 `Conflict`，不静默删除；删除整个项目走 `workspace_project_delete` / `ProjectService::delete_project` |
| `planning_list_projects` | 只列出项目当前计划（`is_active=1`）与尚未补链的遗留计划，避免一个项目在规划中心出现多份身份 |
| MCP `taskdock_create_project` / `taskdock_update_project` / `taskdock_update_plan` | 创建走统一创建服务；项目根写走 `update_project_fields_tx`；计划写走 `update_plan_tx`；三者均强制版本令牌 |

### 10.2 创建幂等：请求摘要与归属（v92 更新）

- 幂等键：`clientRequestId`（前端同一草案重试复用，成功后清空，参数变化换新——
  Workbench 按参数摘要派生：同参数重试保持同一 requestId、参数变化重新生成、
  处理中禁改关键字段、关闭弹窗保留）。
- **归属作用域（v92）**：幂等查询按
  `(principal_kind, principal_id, client_request_id)` 在 `project_create_requests`（迁移 v92）
  精确匹配——同一主体 + 同摘要返回既有项目；同主体 + 不同摘要 → `Conflict`；
  **不同主体（人或另一个 Agent）相同请求 ID 各自独立创建**，任何主体不能通过重放
  获得其他主体创建的项目或其授权。
- 历史兜底：v92 之前的 `project_events(kind='project_created', actor='user')` 只对
  本机人类生效（按旧摘要判定）；Agent 请求一律走新表，不进入兜底。
- 摘要：后端对**清洗后的规范化参数**计算 SHA-256（`requestDigestV2`），写入
  `project_create_requests.request_digest` 与 `project_events.payload_json`；
  事件 payload 同时记录真实主体 `principal{principalKind, principalId}`。

## 16. 统一项目创建服务（2026-11-21）

| 层 | 契约 |
|---|---|
| 领域服务 | `project_hub::creation::create(db, CreateProjectRequest) -> ProjectCreateResult`（人类 UI：目录初始化与补偿在事务外） |
| 事务内变体 | `creation::create_with_conn(conn, request)`（拒绝 `create_new`，供既有写事务） |
| **Agent 统一用例** | `agent_access::project_creation::create_for_agent(_in_conn)`：行 ID fail-closed → 拒 create_new → scope 重读 → `projects.create` → 创建 → **仅当 `created.created == true` 时**项目根自动授权，**单事务**；幂等重放（created=false）不写授权，撤权无法被重放恢复；CLI/MCP/REST 三入口共用 |
| IPC | `project_create(input)`（工作台快速创建） |
| IPC（兼容） | `project_hub_create_project(input)` → 转调同一服务，返回快照 |
| CLI | `taskdock project create --name ... [--dir-mode ...]`（`create_new` 仅限本机人类；Agent 拒绝并提示人类在 UI 完成）；`taskdock project update <id> --base-revision N [--name/--description/--status active\|archived/--target-date]`（`--base-revision` 必填，走项目根服务；缺字段与缺令牌均拒绝） |
| MCP | `taskdock_create_project`（经统一用例：scope + `projects.create` + 授权同事务；只允许 `metadata_only` / `attach_existing`） |
| REST | `POST /api/v1/projects`（Agent 经统一用例；拒绝 `create_new`） |

请求字段：`clientRequestId` / `name` / `kind` / `description` / `goal` / `targetDate` /
`templateId` / `rootPath` / `directoryMode` / `devProjectId` / `note` / `planName` /
`initialPlan{goals,phases,features,tasks,capabilities}` / `agentAccessPolicy`；
服务内部从已解析 Principal 构造 `principal`（幂等归属，不对外传）。

返回：`created`（false = 幂等重放）/ `project`（`id` = projectId）/ `activePlan`（`id` = planId）/
`workspace{rootPath,rootExists,devProjectId,provisioningStatus}` / `provisioningStatus`。

错误：`Validation`（模式与路径不自洽、父目录缺失、目录是文件）、`Conflict`（同请求 ID 不同参数、
`create_new` 目标已存在）、`Forbidden`（缺少 `projects.create`）、`NotFound`（关联开发项目不存在）。

幂等：`project_create_requests`（v92）按主体 × 请求 ID 落归属行（UNIQUE 约束），
`project_events(kind='project_created')` 保存 `clientRequestId` + `requestDigest`(V1) +
`requestDigestV2` + `principal`；V2 覆盖全部持久化字段（含目录模式、备注、计划状态、授权策略）。

REST `PATCH /api/v1/projects/{projectId}`（**项目根聚合**）：需 `projects.write` 能力 +
该项目根 grant（计划 ID 入参先解析根）；body 支持 `name` / `kind` / `description` / `goal` /
`lifecycleStatus(active|archived)` / `targetDate` 三态 + `expectedRevision`（根 revision，
**必填**，缺失 400）；旧 `status` 传计划执行状态 → 400 并指路计划端点；返回 `ProjectSummary`
（revision = 根 revision）；版本冲突 409；空补丁（只有 expectedRevision）→ 400「没有可更新的字段」。

REST `PATCH /api/v1/plans/{planId}`（**计划聚合，严格 PlanId**）：授权锚定项目根；body 支持
`status(planning|in_progress|paused|completed)` / `sortOrder` + `expectedRevision`（计划 revision，
**必填**）；**不接受** name/description/targetDate（属项目根）；项目根 ID → 400 Validation；
未知 ID → 404；返回 `PlanningProject`；不改项目根生命周期；空补丁 → 400。
`GET /api/v1/plans/{planId}` 同样严格：项目根 ID → 400，未知 → 404；项目根到活动计划用
`GET /api/v1/plans/current` 或 `GET /api/v1/projects/{projectId}`（含 activePlanId）。

MCP 对应 `taskdock_get_plan` / `taskdock_update_plan`；`taskdock_list_projects` / `get_project` /
`update_project` 返回/更新**项目根读模型**（projectId=根、根 revision、activePlanId、
plans 列表），`project_id` 参数接受旧计划 ID 并解析为根。
`taskdock_update_plan` 的操作与审计资源身份是 `plan`（`resource_id=PlanId`，`project_id=根`，
`revision=计划 revision`）；`planning-changed` 事件同时带 `kind:"plan"` 与 `planId`。
