# 项目中枢：架构设计

> 版本：2026-11-18 设计基线（v78 数据层与项目中枢最小读写入口已实施；完整 UI/能力/版本能力见 `07-迭代计划.md`）
> 本文是 TaskDock「规划 + 能力 + 执行」统一模块的**唯一设计源**。
> 模块内部分文档：审计 `01-现状审计.md`、功能矩阵 `03-功能矩阵.md`、
> 数据模型 `04-数据模型与迁移.md`、服务接口 `05-服务与接口.md`、
> 验收 `06-验收标准.md`、迭代 `07-迭代计划.md`。
> 冲突处理：代码与可复现结果优先；本文与代码不一致时以代码为准并更新本文。

## 1. 产品定位

TaskDock 不再让用户「先成为项目经理」。用户只需要说明想完成什么，系统负责把目标变成
可执行的项目结构，并在执行过程中持续调整。

一句话定位：

> **项目中枢 = 目标驱动的项目执行体系**：从一个想法开始，生成可修改的规划，分析所需能力，
> 组织任务与工作空间，承接产出与反馈，直到交付。

### 1.1 它不是什么

- 不是「规划中心 + 能力中心」的页面拼接，也不是第三套项目系统。
- 不是自动化流水线：所有生成结果都是**草案**，必须可查看、可修改、可撤销。
- 不是任务中心的替代品：任务中心仍是跨项目统一调度入口。
- 不是工作空间的替代品：工作空间仍是实际干活的地方。
- 不是 AI 产品：没有 AI 服务时，全部基础功能必须可用。

### 1.2 三个不变量

1. **唯一项目根**：一个项目只有一条主记录（`workspace_projects`），规划、能力、任务、
   交付物、工作空间都是它的子结构或弱引用。
2. **唯一任务数据**：项目内任务与全局任务是同一行 `tasks`，只增删关联，不复制内容。
3. **单一写路径**：同一业务事实只允许一个服务写入；UI 只调用服务，不自行拼装写操作。

## 2. 核心工作流

```
想法（自然语言）
   │ parseProjectIntent（本地规则；可选 AI 端口）
   ▼
项目意图（类型 / 目标 / 显式约束 / 不确定性）
   │ generateProjectDraft（模板 + 显式信息，推断项标注）
   ▼
项目草案（名称 / 目标 / 阶段 / 里程碑 / 能力需求 / 初始任务 / 工作空间建议）
   │ 用户确认 / 局部修改 / 跳过
   ▼
项目（workspace_projects）+ 计划（planning_projects）+ 阶段（planning_milestones）
   │
   ├─ 能力需求 ── analyzeProjectCapabilities ── 缺口 + 方案（学习/资源/替代/降范围）
   ├─ 任务      ── createProjectTasks ──────── 同一 tasks 表 + 关联
   └─ 工作空间  ── linkWorkspaceToProject ──── 根目录/多目录 + 专业模块
   ▼
执行（任务状态、交付物、工作空间产出）
   │ syncProjectTaskProgress / syncWorkspaceDeliverables（事件驱动，非全量）
   ▼
总览（四项进度 / 能力准备度 / 风险 / 下一步）
   │ 用户指令：「先不做联机功能」
   ▼
规划调整（diff 预览 → 校验 → 确认 → 应用 → 版本记录）
   └──────────────── 回到执行 ────────────────┘
```

### 2.1 关键设计取舍

| 取舍 | 决定 | 理由 |
|---|---|---|
| 项目与规划是一对一还是一对多 | **一对多**（一个项目可有多个计划版本/计划容器，只有一个 active） | 规划调整需要保留历史；一份计划无法承载「调整前后对比」 |
| 规划项目是否独立存在 | **不再独立**：`planning_projects` 收敛为计划容器，必须挂在项目上 | 否则「我的项目」仍有两份 |
| 能力与资源是否同一实体 | **否**：能力是「能不能做」，资源是「有没有可调用的东西」 | 安装 Skill ≠ 掌握能力；一个能力可由多个资源支撑 |
| 阶段模板是否入库 | **v1 用代码常量**，计划只记 `template_id` | 模板不是用户数据；入库会变成第六套配置系统 |
| 任务是否新增状态 | **否**：保持 pending/completed | 改 CHECK 需重建表；延期/取消可由日期与关联表达 |
| 是否新建 Agent 执行层 | **否**：只定义端口与事件，执行仍由外部 Agent | 避免第二套 Agent 运行时 |

## 3. 分层架构

```
┌ UI 层（工作台）
│  项目中枢视图（总览/规划/能力/项目资源/执行）  ← 只渲染读模型，不算业务
│  创建面板（自然语言 / 模板 / 手动）
├ 领域服务层（前端纯逻辑 + Rust 权威实现）
│  intent / draft / revision / progress / capability / integrity
│  —— 前端版本用于即时预览与本地模式；Rust 版本是落库前的最终校验
├ 应用服务层（Rust，单一写路径）
│  ProjectService / ProjectPlanningService / ProjectCapabilityService
│  ProjectTaskService / ProjectWorkspaceService / ProjectProgressService
│  ProjectResourceService / ProjectIntegrityService
├ 存储层
│  SQLite（单一写连接 + 事务）；append-only 迁移；BACKUP_TABLES 全登记
└ 外部能力端口
   IntentProvider（local | agent | future model）
   ResourceProvider（knowledge / skill / mcp / agent / tool / workflow）
```

### 3.1 为什么前端也有一份领域逻辑

- **本地基础模式**必须在没有 Rust 服务、没有 AI 时也能给出草案预览（例如工作台启动早期、
  预览 harness、单元测试）。
- 但**前端不得直接落库**：所有写操作仍走 Rust 命令；前端逻辑的结果作为「请求体」提交，
  由 Rust 重新校验（结构、引用、权限）。
- 两份实现必须有同一组契约测试向量（`src/lib/projectHub/__fixtures__`），防止口径漂移。

### 3.2 权限与安全边界

| 场景 | 规则 |
|---|---|
| 项目读写 | 只允许当前本机用户；跨设备同步不在本阶段 |
| 能力/资源引用 | 只读引用既有资源；不因项目删除而删除共享资源 |
| 文件路径 | 只登记绝对路径；复用 `file_workspace::validate_abs_path`；不移动/不覆盖/不删除外部文件 |
| AI/外部 Agent | 默认关闭；显式开启后才发送**最小上下文**（目标 + 阶段 + 能力名，不含正文/路径/密钥） |
| 生成结果 | 必须先结构校验（类型、枚举、引用存在、数量上限）再入草案；不得直接写正式数据 |
| 删除 | 先 `validateProjectIntegrity`；有共享引用时只解除关联；已完成任务不静默删除 |

## 4. 统一数据模型（概念层）

```
Project（workspace_projects，唯一项目根）
├─ Goal[]（project_goals；goal/subgoal 树）
├─ Plan[]（planning_projects；计划容器，active_plan_id 指向当前）
│   ├─ Phase[]（planning_milestones，kind=phase）
│   ├─ Milestone[]（planning_milestones，kind=milestone）
│   ├─ Feature[]（planning_features；可交付工作单元）
│   │   └─ Step[]（planning_feature_steps）
│   ├─ PlanVersion[]（plan_versions；快照/对比/恢复）
│   └─ Activity[]（planning_activity；计划内事件）
├─ CapabilityRequirement[]（project_capability_requirements）
│   └─ Capability（project_capabilities，全局库，多项目复用）
│       └─ ResourceLink[]（capability_resource_links → Skill/MCP/知识库/Agent/工具/模板/工作流）
├─ TaskLink[]（workspace_task_links / task_plan_links / task_capability_links）
├─ Deliverable[]（project_deliverables；计划产出 vs 实际产出 vs 验收）
├─ Workspace（workspace_projects 自身字段 + root_path + 多目录）
│   ├─ Item[]（workspace_items；执行事项树）
│   ├─ CreativeModule 数据（novel/game/comic/general/dev，按 kind）
│   └─ ResourceLink[]（workspace_resource_links；笔记/会话/产物）
├─ ProjectEvent[]（project_events；跨域事件流）
└─ Knowledge/Notes/Agent 弱引用（既有表，不复制）
```

### 4.1 四种「进度」必须分开

| 指标 | 定义 | 无数据时 |
|---|---|---|
| 任务完成率 | 项目关联任务中 `completed / total` | `null` + 「尚无关联任务」 |
| 阶段完成率 | 已完成阶段 / 已定义阶段；阶段完成 = 该阶段功能与必需交付物全部完成 | `null` + 「尚无阶段」 |
| 里程碑完成率 | 已完成里程碑 / 里程碑总数 | `null` + 「尚无里程碑」 |
| 项目整体进度 | **各阶段内部完成率的算术平均**（每个阶段等权）；无阶段时回退到任务完成率并标注来源 | `null` + 「尚无可计算进度」 |

禁止把四个数字加权成一个不透明百分比；UI 必须分列并标注来源。整体进度只在用户明确选择
「按阶段等权」时展示。

### 4.2 能力准备度（可解释公式）

对每个能力需求：

```
necessity ∈ {required(权重3), recommended(2), optional(1)}
mastery   ∈ {expert(1.0), proficient(0.85), basic(0.6), learning(0.3), none(0), unknown(未评估)}
resource  ∈ {available(1.0), partial(0.6), none(0), unknown(未评估)}
```

输出**两个独立指标**：

- 掌握度 = Σ(权重 × mastery) / Σ(权重)，仅统计 `mastery != unknown` 的需求；
- 资源可用度 = Σ(权重 × resource) / Σ(权重)，仅统计 `resource != unknown` 的需求；
- `unassessedRequired` = 未评估的必需能力数量；
- 结论标签：
  - `unassessed`：必需能力全部未评估，或 `unassessedRequired / requiredTotal > 50%`；
  - `blocked`：存在必需能力 `mastery=none && resource∈{none,unknown}`；
  - `partial`：有缺口但有替代/可得资源；
  - `ready`：全部必需能力至少 `basic` 或有可用资源。

UI 必须展开「按能力」的明细（阶段、必需性、掌握度、资源、替代方案、影响），不得只显示一个百分比。

### 4.3 项目与工作空间的数据所有权

| 数据 | 所有者 | 工作空间权限 | 项目中枢权限 |
|---|---|---|---|
| 项目名称/类型/状态/根目录 | 项目（workspace_projects） | 只读展示 | 读写 |
| 计划/阶段/功能 | 计划服务 | 只读（显示当前阶段） | 读写 |
| 事项（items） | 工作空间 | 读写 | 只读汇总 |
| 任务内容 | 任务中心 | 只读（通过关联） | 只读（通过关联）+ 创建草稿 |
| 交付物 | 项目服务 | 上报（登记/更新状态） | 读写/验收 |
| 能力/需求/缺口 | 能力服务 | 只读 | 读写 |
| 知识库/Skill/MCP | 各自模块 | 只读引用 | 只读引用 + 关联 |

**不出现两份相同数据**：工作空间不存项目目标/阶段，项目中枢不存事项/任务正文。
工作空间通过 `getWorkspaceProjectContext(workspaceId)` 读项目上下文；项目中枢通过
`syncWorkspaceDeliverables` 读交付物事实。

## 5. 五种工作模式的统一与差异

**统一核心模型**：项目、计划、阶段、功能、任务、交付物、能力需求、事件，五种模式完全一致。

**场景扩展**只体现在三处：

1. **阶段模板**（代码常量，可编辑）
2. **工作空间 Profile**（既有 `workspaceProfiles.ts`，决定专业模块）
3. **专业数据表**（既有 v59–v63，按 kind 归属）

| 模式 | 默认阶段模板 | 工作空间专业模块（既有） | 能力需求重点 |
|---|---|---|---|
| 小说 `novel` | 世界观 → 人物 → 故事主线 → 分卷 → 章节 → 校对 → 完稿 | 正文（卷/章）、人物、世界观 | 写作、结构设计、校对、资料检索 |
| 游戏 `game` | 创意设计 → GDD → 原型 → 核心玩法 → 美术 → 音频 → 测试 → 发布 | 制作事项、游戏资源、构建与测试 | 程序、引擎、2D/3D 美术、音频、测试 |
| 漫剧 `ai_comic` | 故事策划 → 剧本 → 分镜 → 角色 → 场景 → 画面 → 配音 → 剪辑 → 发布 | 剧集、分镜、角色与场景、素材与产物 | 编剧、分镜、绘画/生成、配音、剪辑 |
| 通用 `general` | 自定义（默认：准备 → 执行 → 复查 → 完成） | 阶段与里程碑、项目资料、事项 | 由用户定义，允许全空 |
| 开发 `development` | 需求 → 架构 → 设计 → 开发 → 测试 → 部署 → 维护 | 开发事项、仓库与风险、Agent 接续、构建与验收 | 语言/框架、测试、部署、代码审查 |

规则：

- 模板生成的所有条目 `source=template`，用户可改名/删除/排序/跳过；不强制填满。
- 专业模块能力状态继续遵守 `available / limited / planned / unavailable` 四态闸门，
  未实现的能力不得给可点击入口。
- 不同模式不共享「阶段完成」判定：小说按章节/校对，游戏按构建与测试，漫剧按集/镜头，
  通用按交付物，开发按验收记录；判定函数由 Profile 的 `phaseCompletionPolicy` 声明。

## 6. 信息架构与交互

### 6.1 路由与命名

| 项 | 决定 | 理由 |
|---|---|---|
| 一级入口 | 沿用 workbench 路由 `roadmap`，显示名改为「项目中枢」 | 保留 Ctrl+9、导航显隐、既有测试与深链；不新增一级导航群 |
| 能力中心 | 迁移期保留 `capability` 入口；合入后其内容成为「能力/项目资源」的数据来源 | 能力中心仍在他人未提交工作树中，不能同时改 |
| 项目资源 | 项目中枢内视图名「项目资源」 | 「资源管理」已被系统硬件资源占用，避免同名 |
| 工作空间 | 保持 `workspace` 路由不变 | 执行环境不能消失，也不能被塞进项目页 |
| 任务中心 | 保持 `tasks` 路由不变 | 跨项目统一调度仍是独立职责 |

### 6.2 页面结构（功能信息架构，不强制顶部 Tab）

```
项目中枢
├─ 顶栏：项目选择器（搜索/筛选/最近/归档）+ 新建 + 打开工作空间
├─ 总览（默认）
│   ├─ 目标与当前阶段（一句话 + 阶段名 + 目标日期）
│   ├─ 进度：任务 / 阶段 / 里程碑 / 整体（四列，各自来源与空态）
│   ├─ 能力准备度（掌握度 + 资源可用度 + 待评估标记）
│   ├─ 风险与阻塞（最多 3 条，可展开）
│   ├─ 下一步行动（最多 3 条，可执行/忽略/稍后）
│   └─ 最近产出与活动（时间线，分页）
├─ 规划
│   ├─ 目标树（goal/subgoal）
│   ├─ 路线图（阶段 + 里程碑，横向时间轴/窄屏纵向）
│   ├─ 阶段详情（功能、交付物、能力需求、关联任务）
│   └─ 规划版本（历史、对比、恢复）
├─ 能力
│   ├─ 需求（按阶段分组，必需/建议/可选）
│   ├─ 能力库（分类、掌握度、证据、关联项目）
│   └─ 缺口与方案（学习/资源/替代/降范围）
├─ 项目资源
│   ├─ 知识库 / Skill / MCP / Agent / 工具 / 模板 / 工作流
│   └─ 每条标注：可用性、作用域、最近验证、关联能力
└─ 执行
    ├─ 任务（项目过滤，复用任务中心数据）
    ├─ 交付物（计划/已产出/已验收）
    └─ 工作空间（入口、根目录、多目录、同步状态）
```

### 6.3 新建项目：默认自然语言

```
┌ 你想完成什么？ ──────────────────────────────┐
│ 我要写一本 30 万字的科幻小说，三个月内完成   │  ← 多行输入，支持 IME 回车不提交
├──────────────────────────────────────────────┤
│ [开始规划]  [使用模板]  [手动创建（高级）]   │
└──────────────────────────────────────────────┘
```

- 「开始规划」→ 本地解析（或用户开启 AI 后走 AI 端口）→ 草案预览。
- 「使用模板」→ 选五种模式之一 → 直接生成可编辑草案。
- 「手动创建」→ 保留原有四字段表单（名称/描述/状态/目标日期）+ 类型选择；
  **不得删除既有表单能力**。
- 空输入不得提交；解析失败保留原文并提供「改用模板/手动创建」。

### 6.4 草案预览：渐进式确认

- 卡片式分区：项目名称与类型 / 目标 / 阶段 / 里程碑 / 能力需求 / 初始任务 / 工作空间建议 /
  不确定信息。
- 每个分区：来源标记（你提供 / 模板 / 推断）、单项编辑、整段「重新生成」（本地重算或 AI）、删除。
- 顶部一句话修改框：「把周期改成六个月，先不要做联机功能」→ 只改受影响部分，展示 diff。
- 底部：`确认并创建`（主）/ `跳过非必要设置`（次）/ `返回修改目标`（次）。
- 不确定信息以 chip 呈现；只有**阻塞创建**的问题（如类型无法判定且用户未选）才追问，最多 3 个。
- 未确认前不写数据库；离开时保留草稿（本地 store + localStorage，按项目草稿键隔离）。

### 6.5 规划调整

1. 用户输入指令（自然语言或结构化表单）。
2. `analyzePlanningChange` 产出受影响的目标/阶段/功能/任务/能力/资源。
3. `generatePlanningDiff` 生成前后差异（新增/删除/修改/移动），删除项必须显式列出
   受影响任务与已完成项。
4. `validatePlanningRevision`：引用完整性、已完成任务保护、共享资源引用、循环依赖。
5. 用户确认 → `applyPlanningRevision` 单事务应用 → `plan_versions` 快照。
6. 任何时候可 `rollbackPlanningRevision` 到历史版本；恢复前再次校验。

### 6.6 响应式与密度

| 容器宽度 | 规则 |
|---|---|
| ≥ 900px | 总览两栏（左：目标/进度/能力；右：风险/下一步/活动）；规划为横向路线图 |
| 640–899px | 总览单栏；路线图纵向；阶段详情两栏折叠为一栏 |
| < 640px | 全部单栏；视图切换为分段控件可横向滚动；统计四项 2×2；长文本截断 + 详情展开 |
| < 420px | 隐藏次要元数据（更新时间、来源标签缩写）；操作收进「更多」菜单 |

- 空状态不超过 3 行文案 + 一个主操作，不占满整屏。
- 不用大量卡片堆叠：总览最多 5 个区块，其余渐进展开。
- 沿用语义 Token（`--surface-*`、`--text-*`、`--border-*`、`--accent-gradient`），
  不新增平行组件、不硬编码颜色。

## 7. AI 增强与本地基础双模式

### 7.1 现状事实

TaskDock 当前**没有模型客户端**：`agents` 只读监控外部会话，MCP Server 只暴露自身工具。
因此「AI 增强模式」是一个**端口设计**，不是既有能力。

### 7.2 端口定义

```ts
interface ProjectIntentProvider {
  readonly id: "local" | "agent";
  available(): Promise<boolean>;
  parse(input: string, signal?: AbortSignal): Promise<ProjectIntent>;
  draft(intent: ProjectIntent, signal?: AbortSignal): Promise<ProjectDraft>;
  revise(draft: ProjectDraft, instruction: string, signal?: AbortSignal): Promise<ProjectDraftRevision>;
}
```

- `local`：默认，纯规则，离线可用，零网络。
- `agent`：后续通过外部 Agent（用户授权）或 MCP 工具实现；未实现前 `available()` 返回 false。
- 选择策略：用户设置开启 + 端口可用 → agent；否则 local。**不允许静默回退后假装是 AI 结果**，
  UI 必须标注来源。

### 7.3 失败与恢复

| 情况 | 行为 |
|---|---|
| 请求超时（默认 20s） | 中止，保留已输入内容，提供「重试 / 改用本地 / 手动创建」 |
| 请求失败 | 同上；不得清空草稿 |
| 输出结构错误 | 拒绝写入草案；展示「生成结果格式不正确」，记录诊断（不含正文） |
| 部分成功 | 逐段标记成功/失败；失败段可单独重试，已成功段保留 |
| 用户取消 | `AbortSignal` 中止；不写任何数据 |
| 重试 | 同一输入幂等；不重复创建项目 |

### 7.4 生成结果的校验闸门

进入草案前必须通过：

1. 枚举合法（kind/status/priority/necessity/mastery/resource）；
2. 引用存在（phaseId/capabilityKey 在草案内可解析）；
3. 数量上限（阶段 ≤ 30、每阶段功能 ≤ 50、能力需求 ≤ 100、初始任务 ≤ 100）；
4. 文本长度（名称 ≤ 120、描述 ≤ 4000、单项标题 ≤ 240）；
5. **不得虚构**：没有显式日期的 `targetDate` 必须为 `null`；预算未提及必须为 `null`；
6. 每个字段必须带 `source`（user/template/inferred/default）与可选 `note`。

## 8. 性能、可靠性与安全

| 项 | 要求 |
|---|---|
| 总览读取 | 单次批量查询聚合；不遍历文件；不 N+1；60s 内存缓存 + `computedAt`；切项目立即失效 |
| 进度计算 | 增量：任务状态变更事件只重算受影响阶段；规划修改只重算受影响项目 |
| 工作空间同步 | 只上报交付物与阶段事实；不监听目录；文件变化不触发全项目重算 |
| 多项目切换 | 请求代际 + 作用域校验；旧响应不得写入新项目（沿用 planning store 的 seq 模式） |
| 并发 | 单写连接 + 事务；`revision` 乐观并发；重复提交幂等 |
| 取消 | 所有异步服务支持 `AbortSignal`；后台任务可回收 |
| 路径安全 | 复用 `validate_abs_path`；拒 UNC；只登记不写入 |
| 共享资源 | 删除前检查引用；`SET NULL` 而非级联删除 |
| 审计 | 事件只记元数据/摘要；不记正文、密钥、完整路径 |
| 移动端 | 本阶段只读接口预留；不新增编辑页面 |

## 9. 兼容性要求（不可破坏）

1. `planning_*`、`workspace_*`、`tasks` 的现有命令签名与返回结构不变；新增字段必须
   `#[serde(default)]`，前端旧版本可读。
2. 迁移只追加在 `MIGRATIONS` 末尾；不改已发布迁移；不重建已发布表（除既有 v57 式必要重建，
   且必须自检 + 回滚）。
3. 备份：新表全部登记 `EXTENDED_TABLES` + `BACKUP_TABLES`，给出 `restore_order` 与依赖；
   旧备份恢复后新表为空，读侧按「未评估/无阶段」降级。
4. `planning_projects` 原 ID 不变；MCP 授权、`feature_agent_links`、活动历史全部继续命中。
5. 导航：`roadmap` Tab id 与 Ctrl+9 不变；`capability` 在迁移期保留。
6. 视觉：只使用语义 Token；不改变主窗口最小尺寸、贴边吸附、DPI 与多显示器逻辑。
7. `tasks.status` 仍为 `pending/completed`；不因新功能改变既有语义。

## 10. 本轮不做（明确边界）

- 不实现 AI 模型调用；只定义端口与本地规则实现。
- 不实现跨设备项目同步。
- 不实现任务三态（进行中/取消）。
- 不重写能力中心的五段页面；迁移期只读引用。
- 不实现移动端项目中枢。
- 不删除 `general_milestones`、`capability_contexts` 等既有结构。
