**关键事实（有代码位置）**

| 事实 | 位置 |
|---|---|
| 规划中心与工作空间是**两套独立项目实体**，各有自己的表、状态与进度 | `db/mod.rs` v18 planning DDL；v49 `workspace_projects`；v57 重建 |
| 规划中心「我的项目」没有 `kind` 字段，无法表达小说/游戏/漫剧/开发/通用 | `commands/planning.rs` `PlanningProject` |
| 工作空间项目没有目标、描述、截止日期字段，无法承载规划语义 | `commands/project_workspace.rs` `WorkspaceProject` |
| 任务只有 `pending / completed` 两态，无「取消 / 进行中」，无项目/阶段/能力维度 | `db/models.rs` `Task`；v1 DDL `status CHECK (pending,completed)` |
| 任务与项目的关联只存在于 `workspace_task_links`（项目侧读，任务中心不展示） | v49 DDL；`TasksPanel.tsx` 无项目筛选 |
| 能力中心没有「能力」实体：只有知识库/Skill/MCP/上下文/配方五类资源 | `capability/schema.rs` v72/v74 |
| 能力中心只能绑定 `workspace_projects`，无法绑定规划项目 | `knowledge_bases.project_id/workspace_id`、`capability_skills.project_id` |
| 项目删除对共享资源是 `ON DELETE SET NULL`，不删除知识库/Skill/上下文/配方 | `capability/schema.rs` |
| MCP Server 直接读写 `planning_*`，并以 `planning_projects.id` 做项目授权 | `mcp/auth.rs:339`、`mcp/tools.rs:492/556/567/743` |
| 备份恢复顺序：planning（260）早于 workspace（435） | `commands/backup.rs` restore rule |
| 没有模型/LLM 客户端；`agents` 是外部会话的只读监控 | `src-tauri/src/agents/`、`commands/agents.rs`（无 generate/completion 命令） |

**判断（架构推论）**

1. 当前系统是「四套并列子系统 + 一个全局任务中心」，缺一个**项目根实体**把规划、能力、
   执行、产出串起来。规划中心与工作空间各自回答「我的项目是什么」，答案不一致。
2. 能力中心回答的是「我有哪些资源」，不是「这个项目需要哪些能力、缺什么、怎么补」。
   两者概念不同，不能靠改页面标题合并。
3. 由于任务中心不感知项目，项目进度只能在工作空间内部计算，规划进度只能在规划中心计算，
   用户看到两个百分比，且都不完整。

## C. 重复功能清单

| # | 重复/冲突 | 证据 | 影响 | 判定 |
|---|---|---|---|---|
| C1 | 两套项目实体 | `planning_projects` vs `workspace_projects` | 用户有两份「我的项目」；能力中心只能绑后者；MCP 只能操作前者 | **必须消除**：以 `workspace_projects` 为项目根 |
| C2 | 两套项目状态 | planning `planning/in_progress/paused/completed` vs workspace `active/archived` | 同一项目两个状态，UI 无法一致表达 | 保留两个轴但**明确语义**：项目生命周期 vs 计划执行状态 |
| C3 | 两套进度 | `ProjectStats`（功能完成率）vs `workspace_project_progress`（事项/任务） | 两个百分比，都自称项目进度 | **必须消除**：统一进度服务，分四项指标输出 |
| C4 | 两套项目入口 | `ProjectsView`（规划）vs `ProjectWorkspacePanel`（工作台）+ 旧 `WorkspaceProjectsPanel` | 用户需在两个页面各建一次项目 | 合并为项目中枢；旧面板退化为只读/移除 |
| C5 | 「能力」四种语义 | `mcp_agent_capabilities`（权限）、`WORKSPACE_CAPABILITIES`（功能可用性）、`capability_skills`（Skill 资源）、`capability.center`（知识/MCP 管理） | 新增「能力」实体时会与既有命名冲突 | 新实体命名 `project_capability`；文档强制三处语义区分 |
| C6 | 资源语义冲突 | `resource` Tab = 硬件资源；能力中心 = 项目资源 | 一级导航「资源管理」已被占用 | 项目内资源 view 命名「项目资源」，一级入口不叫「资源管理」 |
| C7 | 知识库双项目列 | `knowledge_bases.project_id` 与 `workspace_id` 同时指向 `workspace_projects` | 语义重叠，用户不知选哪个 | 后续迁移合并为一个 `project_id`（保留 `workspace_id` 为兼容别名，标注 deprecated） |
| C8 | 里程碑双实现 | `planning_milestones` vs `general_milestones`（v62） | 两个里程碑，通用项目用一个、规划用一个 | **保留但分工**：planning_milestones 为计划阶段/里程碑权威；`general_milestones` 收敛为通用项目的历史实现，后续迁移到统一阶段 |

1. **任务中心**：全部现有视图、提醒、重复、自然语言录入、与 Agent/现场/剪贴板/笔记/场景的关联。

## G. 数据模型调整方案（摘要，详见 `04-数据模型与迁移.md`）

   `active/archived`；新增 `active_plan_id`（弱引用当前计划）。
2. **计划**：`planning_projects` 语义收敛为「计划容器/版本」，新增 `workspace_project_id`
   弱引用与 `template_id`；`name/status/target_date` 保留为计划自身属性，其中
   `target_date` 标注 deprecated，UI 以项目 `target_date` 为准。
3. **阶段**：`planning_milestones` 增加 `kind`（`phase|milestone`）、`start_date`、`status`；
   现有行回填 `kind=milestone`。
4. **能力**：新表 `project_capabilities`（全局能力库，跨项目复用）、
   `project_capability_requirements`（项目 × 能力 × 阶段）、`capability_resource_links`、
   `capability_gap_resolutions`。
5. **交付物**：`project_deliverables`（项目/阶段/路径/状态/验收时间/证据），路径只引用不托管。
6. **版本**：`plan_versions`（项目/计划/序号/快照 JSON/来源/父版本）。
7. **事件**：`project_events`（项目/类型/载荷 JSON/时间），只记元数据与摘要，不记正文/密钥/完整路径。
8. **关联**：`task_plan_links`（任务 ↔ 阶段/里程碑）、`task_capability_links`（任务 ↔ 能力）。
9. **不强改**：`tasks.status` 仍为两态；「延期」由 `due_at` 派生，「取消」用删除 + 解除关联；
   如需三态另立迁移，不在本阶段。
10. **删除策略**：项目删除级联计划/阶段/功能/交付物/需求/版本/事件；任务只解除关联不删除；
    能力库与知识库/Skill/MCP/上下文/配方只 `SET NULL`，不删除。

## H. API 与服务层调整方案（摘要，详见 `05-服务与接口.md`）

## 审计结论

1. 需求方向正确：当前确实存在「两套项目、两套进度、能力与资源混淆、任务无项目维度」四类结构性问题。
2. 但不能靠「合并页面」解决：必须先建立**唯一项目根**与**统一读模型**，否则只是把两套数据画在
   同一个屏上，重复与不一致会更深。
3. 也不能一步推翻：`workspace_projects` 已被 20+ 表引用、五种 Profile 依赖；`planning_*` 被
   MCP Server 与备份系统依赖。可行路径是「项目根 + 计划容器 + 能力层 + 统一读模型」的增量模型，
   全部通过 append-only 迁移与内部服务替换完成。
4. 本轮不实施数据库与 UI 改造，原因是：能力中心仍在他人未提交工作树中、四个核心文档被其他
   任务修改中，此时改共享枢纽文件会把本任务改动混入他人提交。设计先行，实施待集成窗口。
