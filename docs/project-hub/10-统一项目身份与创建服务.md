## 2. 实体关系

```text
Project (workspace_projects)                 项目聚合根：名称/类型/状态/目标/目标日期/root_path
  │  active_plan_id ─────────────┐
  │  dev_project_id ──┐          │
  ├─ ProjectPlan (planning_projects)  ── 计划容器：status/archived/revision/is_active
  │     ├─ Phase (planning_milestones.kind='phase')
  │     ├─ Milestone (planning_milestones.kind='milestone', phase_id→Phase)
  │     ├─ Feature (planning_features, milestone_id→Phase, project_id=plan id)
  │     └─ Task link (task_plan_links: project_id=项目根, phase_id, milestone_id)
  ├─ Goal / CapabilityRequirement / Deliverable / Event / ResourceLink（project_id=项目根）
  ├─ WorkspaceProject 视图 = 本表本身（工作空间是项目的执行面，不是另一个实体）
  └─ AgentWorkspace (agent_workspaces)  ── Agent 文件交换目录，与项目源码目录无关

DevProject (dev_projects)   开发仓库登记（root_path 唯一），项目通过 dev_project_id 弱引用
```

边界（不可混用）：

1. **Project ≠ ProjectPlan**：计划是项目的可替换执行方案；一个项目可有多个计划，只有一个 active。
2. **ProjectWorkspace 不是第二张表**：它就是项目根在工作台里的执行视图（模块布局按 `kind` 从
   `workspaceProfiles.ts` 派生，不落库成第二份项目事实）。
3. **AgentWorkspace ≠ 项目源码目录**：`agent_workspaces.root_path` 是 Agent 的文件交换区，
   永远不写入 `workspace_projects.root_path`，也不参与项目目录初始化。
4. **DevProject 只登记仓库**：`dev_projects` 不因项目删除而级联删除，项目只持有弱引用。

## 3. ID 契约

| 字段 | 语义 | 唯一来源 |
|---|---|---|
| `projectId` | 项目根 ID（`workspace_projects.id`） | 创建服务返回、所有项目级授权与操作记录使用 |
| `planId` | 计划 ID（`planning_projects.id`） | `create_project_plan` / 创建服务返回的 `activePlanId` |
| `activePlanId` | 项目当前计划 ID | `workspace_projects.active_plan_id`，与 `planning_projects.is_active=1` 同事务维护 |

规则：

1. **项目列表只返回项目根**（每个项目一行），`activePlanId` 是摘要字段，不是第二个列表项。
2. **计划列表独立返回计划**（`list_plans` / `GET /api/v1/plans`），条目带 `projectId`。
3. **项目详情返回项目 + activePlan 摘要 + 计划清单**；需要完整计划时单独取计划。
4. **计划 ID 可反解析项目根**：`resolve_project_root(plan_id)`；旧数据缺链时在事务内补建（复用
   `ensure_project_for_plan_tx`），不再返回「planning 项目」这种伪实体。
5. **项目级授权一律用项目根 ID**：迁移 v91 已把 `mcp_agent_grants.project_id` 的外键改到
   `workspace_projects(id)`，计划 ID 不再作为授权目标；旧调用方传计划 ID 时由
   `resolve_project_root` 在判定前解析，不需要重复授权。
6. **旧 Agent API 兼容**：仍接受计划 ID 作为 `{id}` 入参（解析到项目根后返回项目视图），响应里同时
   带 `id`（= projectId）与 `planId` / `activePlanId`，旧字段不删除。

### 4.3 事务边界与顺序

```text
1. 参数清洗（名称/枚举/日期/路径）        ← 纯函数，失败不触碰任何状态
2. 幂等查询（v92 起按归属作用域）
     ├─ 第一优先：project_create_requests 按 (principal_kind, principal_id, client_request_id)
     │    精确查询；命中且 request_digest 一致 → 返回既有结果（created=false），
     │    不建目录、不跑恢复；摘要不同 → Conflict
     ├─ 历史兜底（仅 LocalHuman）：v92 之前的 project_events(kind='project_created',
     │    actor='user') 按 clientRequestId + 旧摘要判定；Agent 请求一律不进入该兜底，
     │    宁可重放视为新请求也不给「跨主体命中旧事件」留通道
     └─ 未命中 → 继续
3. 目录准备（见 §5）：create_new 先写恢复日志（pending）再建目录（created）
     └─ create_new 遇「目标已存在」→ 再查一次幂等，命中则返回既有结果
4. SQL 事务：项目根 + 初始计划 + 阶段/里程碑/功能/任务/目标/能力
     + project_create_requests（归属行，UNIQUE(principal_kind, principal_id, client_request_id)）
     + project_events（payload 记录 principal{principalKind, principalId} 真实主体）
     ├─ 事务内再判一次幂等（并发下以数据库为准，单写连接串行化兜底）
     ├─ 提交成功 → 按 opId 出清恢复日志，返回结果
     └─ 失败 → 回滚目录（仅本次新建的空目录），再向上抛错
5. 事务外：目录恢复扫描（best effort，失败只记录）
6. 事务外：Agent 授权（可选） → 只写刚创建的项目根（v92 起不再写计划 ID 兼容行）
```

**顺序不可调整**：幂等查询必须早于目录初始化。反例（首版缺陷）：`create_new` 第一次成功，
第二次相同请求因「目录已存在」返回 `Conflict`，幂等在最需要它的模式下失效。

**恢复扫描放在创建收尾**（不是创建之前）：创建前扫描会把用户刚选来「关联已有目录」的空目录
当成上次崩溃的孤儿删掉，项目随即变成 `attached_offline`。收尾时本次目录已被项目引用、
在途操作由 `ACTIVE_OPS` 保护，扫描只能命中无人认领的旧目录；崩溃场景仍由启动时的扫描兜底。

**摘要覆盖范围**：所有影响持久化结果的字段都必须进摘要（名称、类型、描述、目标、日期、模板、
`rootPath`、`directoryMode`、`devProjectId`、初始计划全部内容、授权策略）。新增字段一律用
`requestDigestV2` 追加，旧事件只有 `requestDigest`；重放时 V2 命中或旧摘要命中都视为同一请求
（连旧摘要都没有时按「同一请求」兼容），V2 存在时只比较 V2。

**重放的边界**：重放只读当前 `active_plan_id`，不切换计划、不补写计划、不改状态；
因此「创建成功 → 用户切换了当前计划 → 客户端重试」不会再切回创建时的计划。

### 4.4 禁止

- 不在 UI / MCP / CLI / REST 里各写一份创建 SQL；
- 不产生「有项目没有初始计划」或「有计划没有项目」的半成品；
- 不把「目录不存在」当成「创建新目录」；
- 不默认 `git init`。

## 5. 工作目录初始化

### 5.1 三种模式

| 模式 | 前置校验 | 目录已存在 | 目录不存在 | 落库 `root_path` |
|---|---|---|---|---|
| `metadata_only` | 不接受 `rootPath`（传了即校验失败，避免静默丢弃） | — | — | 空 |
| `attach_existing` | 绝对路径 + 非法字符 + 非文件 | 允许（`attached`） | 允许但标 `attached_offline` | 原样（trim） |
| `create_new` | 父目录存在且是目录、目标不存在 | **拒绝**（Conflict） | 创建并验证，`created` | 新建后的路径 |

`attach_existing` 允许离线路径是既有产品行为（移动硬盘/网络盘会临时离线），读侧用
`root_exists` 表达事实；`create_new` 必须由用户显式选择，绝不由「路径不存在」推断。

### 5.2 创建新目录的顺序与补偿

```text
父目录校验 → 目标是否存在（目录/文件/符号链接一律 Conflict）→ 记录真实父目录
→ 写恢复日志（state=pending，opId + pid + 租约）→ create_dir → 状态置 created
→ 建后校验（is_dir + canonicalize 父目录未被替换）→ 进入 SQL 事务
→ 提交成功按 opId 出清日志 / 失败先删本次空目录再出清
```

- **只回滚本次创建的空目录**：`std::fs::remove_dir`（非空必然失败），绝不 `remove_dir_all`；
- 恢复日志条目带 `opId` / `state(pending|created)` / `pid` / `leaseUntil`：本进程在途操作与
  其他进程租约内的操作一律跳过，避免「A 正在创建、B 把 A 的空目录删了」；
  回滚前还会确认该路径没有被任何项目引用。
- 已有目录、已存在文件、父目录缺失一律不动；`create_new` 必须由用户显式选择。
- 进程在「建目录」与「事务提交」之间崩溃 → 下次启动（或下次创建收尾）先跑 `recover_pending`：
  仅当目录为空且**没有任何项目**的 `root_path` 指向它时才删除，否则只出清日志。
- 日志是「恢复手段」而不是新状态机：没有 `provisioning` 常驻状态，就没有需要人工解锁的僵尸项目。

### 5.3 恢复日志（`project_provisioning_journal`）与并发协调

条目结构（`application_settings`，随备份往返）：

| 字段 | 含义 |
|---|---|
| `opId` | 操作身份（一次 `create_new` 一个）。处置只按它定位，不按路径 |
| `path` | 目标目录（仅用于核对与诊断） |
| `state` | `pending`（已声明、目录未建）/ `created`（目录已建、事务结果未知） |
| `pid` | 拥有者进程 |
| `leaseUntilMs` | 租约到期（epoch 毫秒），只对其他进程生效 |
| `clientRequestId` | 仅用于诊断关联，不参与幂等判定 |
| `createdAt` | 写入时间 |

协调规则：

1. **进程内**：`ACTIVE_OPS`（opId 集合，`Drop` 自动摘除，panic 也能释放）精确表示「在途」，
   恢复遇到在途操作直接跳过——这是首版「恢复线程清掉创建线程日志」缺陷的根因修复；
2. **跨进程**：只认租约。租约内跳过，过期才允许回收；
3. **处置按 opId**：旧版本条目没有 `opId`，按「路径 + `createdAt`」定位，绝不误删同路径新条目；
4. **写回收尾重读**：恢复可能耗时（磁盘 IO），收尾在事务内重新读取日志再过滤已处置项，
   并发创建追加的条目不会被旧快照覆盖；
5. **损坏即停**：JSON 解析失败返回 `Unavailable` 并阻止建目录，不把损坏当成「没有日志」；
6. **可观测**：写入/状态更新/出清/恢复失败全部写 `tracing`（error/warn），不静默吞掉。

恢复判定（任一不满足即保留目录）：

| 现场 | 处置 |
|---|---|
| 在途操作（本进程） | 跳过 |
| 其他进程且租约未到期 | 跳过 |
| 目录不存在 | 丢弃条目 |
| 目录不可访问 | 保留条目，下次重试 |
| 已被任一项目引用 | 只出清日志 |
| 目录非空 | 保留目录、出清日志（避免日志无限增长） |
| 空目录且无引用 | `remove_dir`；失败保留条目 |

### 5.4 路径策略（本地绝对路径）

`project_hub::service::root_path_violation()` 是唯一语法判定，`clean_root_path`、
`workspace_path_check`、`workspace_project_save` 共用同一口径：

| 平台 | 接受 | 拒绝 |
|---|---|---|
| Windows | `X:\…`、`X:/…` | UNC `\\server\share` / `//…`、`\\?\…`、`\\.\…`、`C:foo`、相对路径、`<>:"\|?*` 与控制字符 |
| Linux / macOS | `/…` | 相对路径、控制字符 |

- **拒绝 UNC 是产品决策**：`create_new` 与崩溃恢复都依赖「存在性 / 空目录」的可靠判定，
  网络盘断连会把「不可访问」伪装成「不存在」。若将来支持网络目录，必须先补连接可用性探测与
  独立的安全验证，不能只放开校验。
- **比较用归一化相等**：Windows 忽略大小写与分隔符差异、macOS 忽略大小写、Linux 保留大小写；
  路径归属判定不做前缀匹配。
- **符号链接与父目录替换**：目标存在符号链接/junction 一律 `Conflict`；建目录前记录
  `canonicalize(parent)`，建后核对 `canonicalize(target).parent()`，不一致则清理并报错。
- **错误可区分**：不存在 / 权限不足 / 不可访问（网络盘断连）/ 目标是文件，各自返回不同文案。

### 5.5 Git

本阶段只复用 `dev_projects` 与既有 Git 服务：项目可关联已有仓库（`dev_projectId`），
**不自动初始化仓库**。自建 Git 服务器不在本阶段范围。

## 6. 四入口对照

| 入口 | 命令/接口 | 目录模式来源 | 返回 |
|---|---|---|---|
| UI 快速创建 | `project_create`（IPC） | 弹层选择（默认：填了路径 = `attach_existing`，否则 `metadata_only`） | `ProjectCreateResult` |

四入口的共同点：同一清洗、同一事务、同一幂等摘要、同一错误语义（`Validation` / `Conflict` /

## 7. Agent 权限模型

新增能力：

- `projects.create`：**全局能力**（项目还不存在，逐资源授权无意义），必须显式授予；
- `projects.write`：项目级能力（改名/归档/删除等写操作），按项目根授权。

判定链（第二轮 v92 起为**统一授权四层**，`agent_access::permissions::require` 是唯一入口，
CLI / MCP / REST 三协议共用同一判定，任何协议都不能通过换接入绕过权限）：

```text
身份（LocalHuman / RegisteredAgent / FileImport / SystemInternal）
  → scope（readonly / project_rw / disabled；disabled 一律拒绝）
  → 能力（mcp_agent_capabilities：全局 resource_id='' 或精确项目根；
        projects.create 只支持全局）
  → 项目授权（mcp_agent_grants：项目型能力且资源非空且 scope≠readonly 时，
        必须持有该项目根的授权；计划 ID 入参先由 resolve_project_root 解析）
```

能力与授权的职责分工：

| 层 | 表 | 回答的问题 |
|---|---|---|
| scope | `mcp_agents.scope` | 协议级总开关：能不能读、能不能写 |
| capability | `mcp_agent_capabilities` | 会什么（全局或该项目根）；`context.read` 不能赋予任何项目读取权 |
| grant | `mcp_agent_grants` | 能动**哪个项目**（项目根；readonly 是用户显式选择的全局只读，读不逐项目要 grant） |
| 策略 | `CreatorProjectAndPlan` | 创建成功后自动授予：只写刚创建的项目根（capability `projects.read`+`plans.read`+项目级写 + grant 该根），绝不全局、不跨项目继承 |

硬规则：

1. `scope=project_rw` **不等于**可创建项目，必须另有 `projects.create`；
2. `project_rw` 同样**不等于**可写项目：还必须持有 `projects.write` 能力与该项目根 grant；
3. 创建成功后的自动授权只写**刚创建的项目根**，绝不写全局、也不写计划 ID（v91 外键）；
4. `context.read` 不等于任何项目数据权限，上下文装配仍逐项目按授权过滤；
5. 文件导入（`FileImport`）不因导入内容自称的项目 ID 获得创建/写权限；
6. 撤销（scope / 能力 / grant）即时生效：每次请求都从库里重读，无缓存窗口；
7. Agent 项目列表（CLI `project list` / REST `GET /projects`）按授权过滤：全局能力 + readonly
   返回全部；只有项目级授权的 Agent 只看到被授权项目；无任何授权返回 FORBIDDEN；
   分页 `total` 是过滤后的数量。

## 8. 操作生命周期

继续复用 `agent_access/operations.rs`（唯一操作记录表，不新建第二套）：

- 项目创建记录：`action=project.create`、`resource_kind=project`、`resource_id=projectId`；
- `projectId` 关联创建结果的项目根；`revision` 用计划 revision（首次为 1）；
- MCP / CLI / REST 各自在入口处 `classify`/`describe` 时登记，内部服务不重复建记录；
- `AgentOperationHighlight` 使用真实资源 ID（`projectId` / `planId` / `featureId` / `taskId`），
  禁止标题匹配。

## 9. Agent Workspace 文件协议

```text
manifest.json
projects/{projectId}/project.md                 项目事实（名称/类型/状态/目标/root_path）
projects/{projectId}/plans/{planId}/plan.md     该计划的功能与里程碑
projects/{projectId}/context.md                 该项目的上下文投影
projects/{projectId}/architecture/milestones.md
```

- 顶层只按**项目根**分目录，计划一律在 `plans/{planId}/` 下，不再出现「计划作为同级项目」的目录；
- `plans/current.md` 作为兼容指针保留一个版本周期，内容注明所属 `planId`；
- 导入仍走 schema 校验 + revision 校验 + Agent 身份 + 显式授权 + 冲突处理 + 幂等声明 + 审核归档，
  外部文件不得直接改项目根的敏感字段（`kind` / `status` / `root_path` / `active_plan_id`）。

## 10. 迁移与兼容

- 第一轮迁移 **v90**：重建 `mcp_agent_capabilities` 的 `CHECK`，加入 `projects.create` /
  `projects.write`，逐行复制旧授权，不加默认授权（最小权限不变）。
- 第一轮迁移 **v91**：`mcp_agent_grants.project_id` 外键从计划改到项目根，历史授权计划先补根再映射。
- 第二轮迁移 **v92**（`agent_access/schema.rs::MIGRATION_92`）：
  - 新表 `project_create_requests`：幂等请求归属
    （`UNIQUE(principal_kind, principal_id, client_request_id)` + `request_digest` +
    `project_id REFERENCES workspace_projects(id) ON DELETE CASCADE` + `plan_id`）；
    历史事件不回填归属（payload 无此信息），旧事件兜底只对本机人类（`actor='user'`）生效；
  - 重建 `agent_decisions` / `agent_handoffs`：`project_kind` 的 CHECK 扩展为
    `('none','project','planning','workspace')`——新数据统一写 `'project'`（表示项目根），
    旧值 `planning` / `workspace` 保留可读，不删除任何历史行。
- 不改任何已发布迁移的 DDL；新增表/枚举值均向后兼容。
- 兼容：
  - 旧备份恢复后按 `MIGRATIONS` 顺序补 v90→v92，能力行与授权行原样保留
    （`project_create_requests` 已登记备份注册表，随项目根一起备份/恢复）；
  - 旧 `project_events` 无 `requestDigestV2` → 本机人类重放按旧摘要判定；
  - 旧 Agent 请求（v92 之前的 requestId）重放 → 视为新请求独立创建，绝不命中他人项目；
  - 旧计划 ID 入参 → 反解析项目根；旧数据缺项目根 → `ensure_project_for_plan_tx` 补建；
  - 旧 `project_kind` 枚举值（`planning` / `workspace`）→ 保留可读，查询过滤用
    「计划反查」兼容子句匹配历史行；
  - MCP 工具名与旧参数（`name` / `description` / `target_date` / `requestId`）不变。

## 14. 第二轮治理（v92，2026-11-22）

第一轮落地后独立验收发现四类 P1 缺陷，本轮在不推翻第一轮正确实现的前提下修复。

### 14.1 跨 Agent 幂等重放（P1）

缺陷：`check_replay` 只按 `clientRequestId` 查 `project_events`，同一 requestId、同一摘要会让
Agent B 命中 Agent A 创建的项目，随后 CLI / REST / MCP 都可能对重放结果执行自动授权。

修复（§4.1/§4.3 已同步更新）：

- 请求归属 `IdempotencyScope{principal_kind, principal_id, client_request_id}` 贯穿
  `prepare / check_replay / create / create_with_conn / create_in_conn`；
- 新表 `project_create_requests`（v92）以数据库级 UNIQUE 保证「同一主体的同一请求 ID 只对应
  一个项目」；摘要冲突返回 `Conflict`；不同主体相同 requestId 各自独立；
- 历史兜底只对 LocalHuman（`actor='user'` 的旧事件）生效；Agent 请求一律不进入兜底；
- `project_events` payload 记录真实主体（`principal.principalId`），不再只有 `actor=agent`；
- 入口层从**已解析的 Principal** 构造身份，禁止用 `TASKDOCK_AGENT_TOKEN` 环境变量猜测。

单测：`project_hub::creation::tests`（agent_replay / different_agents_isolated /
never_replays_human / grant_retry / concurrent / missing_row_id）。

### 14.2 旧 project_kind 契约收敛（P1）

缺陷：第一轮把 `permissions::project_exists` 的返回值收敛为 `project`/`plan`，但
`agent_handoffs` / `agent_decisions` 的 CHECK 仍是 `none|planning|workspace`——**带项目的
交接创建直接 CHECK 失败**；`sync.rs` 的 task.create 用旧字符串比较（永假）、decision 落库
被旧校验拒绝——**文件导入任务/决策全部失败**。

修复：

- 强类型 `ProjectId` / `PlanId`（`project_hub::service`），`ProjectRef::{Project, Plan}`，
  `resolve_project_ref` / `resolve_project_root` 是唯一解析入口；
- v92 把两表 CHECK 扩为含 `'project'`；新数据统一写 `project_id=项目根` +
  `project_kind='none'|'project'`；入参声明的旧 `project_kind` 不参与判定；
- handoff / decision / report / 导入链路的授权与归属全部按项目根；列表过滤支持
  「计划反查」兼容历史行（`workspace_project_id` 反查子句）；
- `permissions::project_exists` 删除，调用点全部改为 `resolve_project_root(...).is_some()`。

### 14.3 MCP 项目授权对齐 v91（P1）

缺陷：`mcp::auth::grant_project` 仍按 `planning_projects` 检查并直插授权（v91 外键下必失败）；
`mcp::permissions::revoke` 不解析根（撤销失效）；MCP 设置 UI 使用计划列表。

修复（详见 `docs/agent-workspace/permission-model.md` §3）：

- grant / revoke / has / read / write 全部经 `resolve_project_root` 归一到项目根；
  计划 ID 只作为入参兼容；撤销同时清理历史计划 ID 残留行；
- `ensure_grant` / `ensure_can_read_project` 统一走 `agent_access::permissions::ensure_project_grant`；
- `taskdock_update_project` 补 `projects.write` 能力校验（此前只查 grant 不查能力）；
- `McpAccessSection` 数据源改为项目根列表（`workspace_project_list`），授权列表按根 ID 匹配名称；
  能力清单补齐项目族（projects.read/create/write、plans.read、decisions、handoffs、context）。

### 14.4 CLI 目录创建门禁与入口一致性（P1/P2）

- CLI：`RegisteredAgent` 拒绝 `--dir-mode create_new`（MCP / REST 早已拒绝），错误提示人类在 UI
  完成；LocalHuman 放行；scope / 只读 / 能力由统一授权覆盖；
- CLI 操作追踪：`cli_operation_result` 复用 `OperationResult::from_value`，项目创建能得到
  `resourceKind=project` / `resourceId=projectId` / `projectId=projectId`，禁止把 planId 当 projectId；
- REST：新增 `PATCH /api/v1/projects/{projectId}`（`projects.write` + expectedRevision 冲突 409）；
- Workbench 快速创建：requestId 按参数摘要派生——同参数重试保持、参数变化重新生成、
  成功清空、处理中禁改关键字段、关闭弹窗保留（保证取消后重试仍幂等）；
- Agent 项目列表按授权过滤（全局 → 全部；项目级 → 被授权项目；无授权 → FORBIDDEN，
  total 为过滤后数量）。
