# 统一项目身份与项目创建服务（架构与技术方案）

> 状态：**落地中（2026-11-21）**。本文是「TaskDock 项目托管体系 × Agent 项目接入统一治理」的
> 唯一架构口径：先定义 Project / Plan 身份与创建契约，再据此改造 Rust 服务、四类入口（UI / CLI /
> MCP / REST）、Agent 权限、操作记录与工作空间文件协议。
>
> 事实优先级：代码与可复现输出 > 测试证据 > 本文 > 历史报告。凡与实现不一致处，以「§12 落地状态」
> 的实测结论为准，并回改本节。

## 1. 现状核对（源码事实，不是推测）

| 事实 | 证据 |
|---|---|
| 项目根是 `workspace_projects`，计划是 `planning_projects` | `project_hub/schema.rs` v78 注释与 DDL；`insert_project_root_tx` 先插 `workspace_projects` 再插 `planning_projects(workspace_project_id, is_active=1)` |
| 项目根持有 `active_plan_id` | v78 `ALTER TABLE workspace_projects ADD COLUMN active_plan_id`；`activate_plan` 同时改 `is_active` 与 `active_plan_id` |
| 计划名/描述/目标日期是项目字段的**兼容镜像** | `update_project_fields_tx` 注释与 SQL（`UPDATE planning_projects SET name=?…WHERE workspace_project_id=?`） |
| 规划入口丢弃 project_id | `commands/planning.rs::create_project_tx` 写成 `let (_, plan_id) = insert_project_root_tx(...)`，只返回计划 |
| MCP 创建项目按**计划 ID** 自动授权 | `mcp/tools.rs` `taskdock_create_project` 分支：`create_project_tx` 后把 `p.id` 写入 `mcp_agent_grants` |
| Agent 项目列表把同一项目返回两次 | `agent_access/service.rs::list_projects` 同时遍历 `list_projects_impl`（计划）与 `workspace_project_list_impl`（项目根） |
| `project_exists` 只判断「存在于任一表」 | `agent_access/permissions.rs::project_exists` 返回 `planning` / `workspace`，不做计划→项目反解析 |
| 能力白名单没有创建类能力 | `mcp/permissions.rs::CAPABILITIES` 与 `Capability::as_str` 均无 `projects.create` / `projects.write` |
| 能力表 CHECK 是硬约束 | `agent_access/schema.rs` v76 重建 `mcp_agent_capabilities` 并写入 `CHECK (capability IN (...))` |
| 工作目录校验已存在且只判事实 | `project_hub/commands.rs::workspace_path_check_impl`：绝对路径 / 非法字符 / 存在 / 是否目录 / 可访问 |
| 文件系统写入没有事务 | 项目创建全程只有 SQL 事务，`root_path` 只落字符串，从不建目录 |
| Agent 投影按两套 ID 写同一目录族 | `agent_access/projection.rs`：计划写 `projects/{planId}/…`，工作空间项目写 `projects/{projectId}/…` |
| 依赖迁移头是 v89 | `db/mod.rs` `MIGRATIONS` 末尾为 `project_hub::schema::MIGRATION_89` |
| 已有幂等键与摘要 | `project_hub/service.rs::request_digest` + `project_events(kind='project_created', payload_json.requestDigest)` |

结论：**「项目根 + 计划容器」的数据模型已经正确，缺的是身份契约、统一创建服务、目录初始化与
Agent 侧收敛。** 因此本方案不新建项目主表，只补领域服务与适配层。

## 2. 实体关系

```text
Project (workspace_projects)                 项目聚合根：名称/类型/状态/目标/目标日期/root_path
  │  active_plan_id ─────────────┐
  │  dev_project_id ──┐          │
  ├─ ProjectPlan (planning_projects)  ── 计划容器：status/archived/revision/is_active
  │     ├─ Phase (planning_milestones.kind='phase')
  │     ├─ Milestone (planning_milestones.kind='milestone', phase_id→Phase)
  │     ├─ Feature (planning_features, milestone_id→Phase, project_id=plan id)
  │     └─ Task link (task_plan_links: project_id=项目根, phase_id, milestone_id)
  ├─ Goal / CapabilityRequirement / Deliverable / Event / ResourceLink（project_id=项目根）
  ├─ WorkspaceProject 视图 = 本表本身（工作空间是项目的执行面，不是另一个实体）
  └─ AgentWorkspace (agent_workspaces)  ── Agent 文件交换目录，与项目源码目录无关

DevProject (dev_projects)   开发仓库登记（root_path 唯一），项目通过 dev_project_id 弱引用
```

边界（不可混用）：

1. **Project ≠ ProjectPlan**：计划是项目的可替换执行方案；一个项目可有多个计划，只有一个 active。
2. **ProjectWorkspace 不是第二张表**：它就是项目根在工作台里的执行视图（模块布局按 `kind` 从
   `workspaceProfiles.ts` 派生，不落库成第二份项目事实）。
3. **AgentWorkspace ≠ 项目源码目录**：`agent_workspaces.root_path` 是 Agent 的文件交换区，
   永远不写入 `workspace_projects.root_path`，也不参与项目目录初始化。
4. **DevProject 只登记仓库**：`dev_projects` 不因项目删除而级联删除，项目只持有弱引用。

## 3. ID 契约

| 字段 | 语义 | 唯一来源 |
|---|---|---|
| `projectId` | 项目根 ID（`workspace_projects.id`） | 创建服务返回、所有项目级授权与操作记录使用 |
| `planId` | 计划 ID（`planning_projects.id`） | `create_project_plan` / 创建服务返回的 `activePlanId` |
| `activePlanId` | 项目当前计划 ID | `workspace_projects.active_plan_id`，与 `planning_projects.is_active=1` 同事务维护 |

规则：

1. **项目列表只返回项目根**（每个项目一行），`activePlanId` 是摘要字段，不是第二个列表项。
2. **计划列表独立返回计划**（`list_plans` / `GET /api/v1/plans`），条目带 `projectId`。
3. **项目详情返回项目 + activePlan 摘要 + 计划清单**；需要完整计划时单独取计划。
4. **计划 ID 可反解析项目根**：`resolve_project_root(plan_id)`；旧数据缺链时在事务内补建（复用
   `ensure_project_for_plan_tx`），不再返回「planning 项目」这种伪实体。
5. **项目级授权一律用项目根 ID**：迁移 v91 已把 `mcp_agent_grants.project_id` 的外键改到
   `workspace_projects(id)`，计划 ID 不再作为授权目标；旧调用方传计划 ID 时由
   `resolve_project_root` 在判定前解析，不需要重复授权。
6. **旧 Agent API 兼容**：仍接受计划 ID 作为 `{id}` 入参（解析到项目根后返回项目视图），响应里同时
   带 `id`（= projectId）与 `planId` / `activePlanId`，旧字段不删除。

```rust
    pub project: ProjectSummary,          // id = projectId

```

### 4.3 事务边界与顺序

```text
1. 参数清洗（名称/枚举/日期/路径）        ← 纯函数，失败不触碰任何状态
2. 幂等查询（clientRequestId + requestDigest）
     ├─ 命中且摘要一致 → 返回既有结果（created=false），不建目录、不跑恢复
     ├─ 命中且摘要不同 → Conflict
     └─ 未命中 → 继续
3. 目录准备（见 §5）：create_new 先写恢复日志（pending）再建目录（created）
     └─ create_new 遇「目标已存在」→ 再查一次幂等，命中则返回既有结果
4. SQL 事务：项目根 + 初始计划 + 阶段/里程碑/功能/任务/目标/能力 + project_events
     ├─ 事务内再判一次幂等（并发下以数据库为准）
     ├─ 提交成功 → 按 opId 出清恢复日志，返回结果
     └─ 失败 → 回滚目录（仅本次新建的空目录），再向上抛错
5. 事务外：目录恢复扫描（best effort，失败只记录）
6. 事务外：Agent 授权（可选） → 只写刚创建的项目根/计划 ID
```

**顺序不可调整**：幂等查询必须早于目录初始化。反例（首版缺陷）：`create_new` 第一次成功，
第二次相同请求因「目录已存在」返回 `Conflict`，幂等在最需要它的模式下失效。

**恢复扫描放在创建收尾**（不是创建之前）：创建前扫描会把用户刚选来「关联已有目录」的空目录
当成上次崩溃的孤儿删掉，项目随即变成 `attached_offline`。收尾时本次目录已被项目引用、
在途操作由 `ACTIVE_OPS` 保护，扫描只能命中无人认领的旧目录；崩溃场景仍由启动时的扫描兜底。

**摘要覆盖范围**：所有影响持久化结果的字段都必须进摘要（名称、类型、描述、目标、日期、模板、
`rootPath`、`directoryMode`、`devProjectId`、初始计划全部内容、授权策略）。新增字段一律用
`requestDigestV2` 追加，旧事件只有 `requestDigest`；重放时 V2 命中或旧摘要命中都视为同一请求
（连旧摘要都没有时按「同一请求」兼容），V2 存在时只比较 V2。

**重放的边界**：重放只读当前 `active_plan_id`，不切换计划、不补写计划、不改状态；
因此「创建成功 → 用户切换了当前计划 → 客户端重试」不会再切回创建时的计划。

### 4.4 禁止

- 不在 UI / MCP / CLI / REST 里各写一份创建 SQL；
- 不产生「有项目没有初始计划」或「有计划没有项目」的半成品；
- 不把「目录不存在」当成「创建新目录」；
- 不默认 `git init`。

## 5. 工作目录初始化

### 5.1 三种模式

| 模式 | 前置校验 | 目录已存在 | 目录不存在 | 落库 `root_path` |
|---|---|---|---|---|
| `metadata_only` | 不接受 `rootPath`（传了即校验失败，避免静默丢弃） | — | — | 空 |
| `attach_existing` | 绝对路径 + 非法字符 + 非文件 | 允许（`attached`） | 允许但标 `attached_offline` | 原样（trim） |
| `create_new` | 父目录存在且是目录、目标不存在 | **拒绝**（Conflict） | 创建并验证，`created` | 新建后的路径 |

`attach_existing` 允许离线路径是既有产品行为（移动硬盘/网络盘会临时离线），读侧用
`root_exists` 表达事实；`create_new` 必须由用户显式选择，绝不由「路径不存在」推断。

### 5.2 创建新目录的顺序与补偿

```text
父目录校验 → 目标是否存在（目录/文件/符号链接一律 Conflict）→ 记录真实父目录
→ 写恢复日志（state=pending，opId + pid + 租约）→ create_dir → 状态置 created
→ 建后校验（is_dir + canonicalize 父目录未被替换）→ 进入 SQL 事务
→ 提交成功按 opId 出清日志 / 失败先删本次空目录再出清
```

- **只回滚本次创建的空目录**：`std::fs::remove_dir`（非空必然失败），绝不 `remove_dir_all`；
- 恢复日志条目带 `opId` / `state(pending|created)` / `pid` / `leaseUntil`：本进程在途操作与
  其他进程租约内的操作一律跳过，避免「A 正在创建、B 把 A 的空目录删了」；
  回滚前还会确认该路径没有被任何项目引用。
- 已有目录、已存在文件、父目录缺失一律不动；`create_new` 必须由用户显式选择。
- 进程在「建目录」与「事务提交」之间崩溃 → 下次启动（或下次创建收尾）先跑 `recover_pending`：
  仅当目录为空且**没有任何项目**的 `root_path` 指向它时才删除，否则只出清日志。
- 日志是「恢复手段」而不是新状态机：没有 `provisioning` 常驻状态，就没有需要人工解锁的僵尸项目。

### 5.3 恢复日志（`project_provisioning_journal`）与并发协调

条目结构（`application_settings`，随备份往返）：

| 字段 | 含义 |
|---|---|
| `opId` | 操作身份（一次 `create_new` 一个）。处置只按它定位，不按路径 |
| `path` | 目标目录（仅用于核对与诊断） |
| `state` | `pending`（已声明、目录未建）/ `created`（目录已建、事务结果未知） |
| `pid` | 拥有者进程 |
| `leaseUntilMs` | 租约到期（epoch 毫秒），只对其他进程生效 |
| `clientRequestId` | 仅用于诊断关联，不参与幂等判定 |
| `createdAt` | 写入时间 |

协调规则：

1. **进程内**：`ACTIVE_OPS`（opId 集合，`Drop` 自动摘除，panic 也能释放）精确表示「在途」，
   恢复遇到在途操作直接跳过——这是首版「恢复线程清掉创建线程日志」缺陷的根因修复；
2. **跨进程**：只认租约。租约内跳过，过期才允许回收；
3. **处置按 opId**：旧版本条目没有 `opId`，按「路径 + `createdAt`」定位，绝不误删同路径新条目；
4. **写回收尾重读**：恢复可能耗时（磁盘 IO），收尾在事务内重新读取日志再过滤已处置项，
   并发创建追加的条目不会被旧快照覆盖；
5. **损坏即停**：JSON 解析失败返回 `Unavailable` 并阻止建目录，不把损坏当成「没有日志」；
6. **可观测**：写入/状态更新/出清/恢复失败全部写 `tracing`（error/warn），不静默吞掉。

恢复判定（任一不满足即保留目录）：

| 现场 | 处置 |
|---|---|
| 在途操作（本进程） | 跳过 |
| 其他进程且租约未到期 | 跳过 |
| 目录不存在 | 丢弃条目 |
| 目录不可访问 | 保留条目，下次重试 |
| 已被任一项目引用 | 只出清日志 |
| 目录非空 | 保留目录、出清日志（避免日志无限增长） |
| 空目录且无引用 | `remove_dir`；失败保留条目 |

### 5.4 路径策略（本地绝对路径）

`project_hub::service::root_path_violation()` 是唯一语法判定，`clean_root_path`、
`workspace_path_check`、`workspace_project_save` 共用同一口径：

| 平台 | 接受 | 拒绝 |
|---|---|---|
| Windows | `X:\…`、`X:/…` | UNC `\\server\share` / `//…`、`\\?\…`、`\\.\…`、`C:foo`、相对路径、`<>:"\|?*` 与控制字符 |
| Linux / macOS | `/…` | 相对路径、控制字符 |

- **拒绝 UNC 是产品决策**：`create_new` 与崩溃恢复都依赖「存在性 / 空目录」的可靠判定，
  网络盘断连会把「不可访问」伪装成「不存在」。若将来支持网络目录，必须先补连接可用性探测与
  独立的安全验证，不能只放开校验。
- **比较用归一化相等**：Windows 忽略大小写与分隔符差异、macOS 忽略大小写、Linux 保留大小写；
  路径归属判定不做前缀匹配。
- **符号链接与父目录替换**：目标存在符号链接/junction 一律 `Conflict`；建目录前记录
  `canonicalize(parent)`，建后核对 `canonicalize(target).parent()`，不一致则清理并报错。
- **错误可区分**：不存在 / 权限不足 / 不可访问（网络盘断连）/ 目标是文件，各自返回不同文案。

### 5.5 Git

本阶段只复用 `dev_projects` 与既有 Git 服务：项目可关联已有仓库（`dev_projectId`），
**不自动初始化仓库**。自建 Git 服务器不在本阶段范围。

## 6. 四入口对照

| 入口 | 命令/接口 | 目录模式来源 | 返回 |
|---|---|---|---|
| UI 快速创建 | `project_create`（IPC） | 弹层选择（默认：填了路径 = `attach_existing`，否则 `metadata_only`） | `ProjectCreateResult` |
| UI 高级创建 | `project_hub_create_project`（IPC） | 请求体 `directoryMode`，项目中枢不建目录（默认 `metadata_only`） | 结果 + 快照 |

四入口的共同点：同一清洗、同一事务、同一幂等摘要、同一错误语义（`Validation` / `Conflict` /

## 7. Agent 权限模型

新增能力：

- `projects.create`：**全局能力**（项目还不存在，逐资源授权无意义），必须显式授予；
- `projects.write`：项目级能力（改名/归档/删除等写操作），按项目根授权。

判定链（保持既有顺序）：

```text
身份（LocalHuman / RegisteredAgent / FileImport / SystemInternal）
  → scope（readonly / project_rw / disabled）
  → 能力（projects.create 需全局；projects.write 需项目根授权）
  → 项目授权（mcp_agent_grants，按项目根；计划 ID 先反解析）
```

硬规则：

1. `scope=project_rw` **不等于**可创建项目，必须另有 `projects.create`；
2. 创建成功后的自动授权只写**刚创建的项目根**，绝不写全局、也不写计划 ID（v91 外键）；
3. `context.read` 不等于任何项目数据权限，上下文装配仍逐项目按授权过滤；
4. 文件导入（`FileImport`）不因导入内容自称的项目 ID 获得创建/写权限。

## 8. 操作生命周期

继续复用 `agent_access/operations.rs`（唯一操作记录表，不新建第二套）：

- 项目创建记录：`action=project.create`、`resource_kind=project`、`resource_id=projectId`；
- `projectId` 关联创建结果的项目根；`revision` 用计划 revision（首次为 1）；
- MCP / CLI / REST 各自在入口处 `classify`/`describe` 时登记，内部服务不重复建记录；
- `AgentOperationHighlight` 使用真实资源 ID（`projectId` / `planId` / `featureId` / `taskId`），
  禁止标题匹配。

## 9. Agent Workspace 文件协议

```text
manifest.json
projects/{projectId}/project.md                 项目事实（名称/类型/状态/目标/root_path）
projects/{projectId}/plans/{planId}/plan.md     该计划的功能与里程碑
projects/{projectId}/context.md                 该项目的上下文投影
projects/{projectId}/architecture/milestones.md
```

- 顶层只按**项目根**分目录，计划一律在 `plans/{planId}/` 下，不再出现「计划作为同级项目」的目录；
- `plans/current.md` 作为兼容指针保留一个版本周期，内容注明所属 `planId`；
- 导入仍走 schema 校验 + revision 校验 + Agent 身份 + 显式授权 + 冲突处理 + 幂等声明 + 审核归档，
  外部文件不得直接改项目根的敏感字段（`kind` / `status` / `root_path` / `active_plan_id`）。

## 11. 测试与验收

Rust（`cargo test --lib`，定向模块）：

| 用例 | 断言 |
|---|---|
| 项目根 + 初始计划 | 同事务创建，`active_plan_id` = 计划 ID，`is_active=1` |
| 计划 → 项目反解析 | 传计划 ID 取详情，返回 `projectId` = 项目根 |
| 多计划 | 第二个计划不抢 active；`activate_plan` 后 `active_plan_id` 跟随 |
| 事务回滚 | 初始计划非法 → 项目根不落库 |
| 幂等重放 | 同 ID 同参 → `created=false`，行数不变 |
| 摘要冲突 | 同 ID 不同参 → `Conflict` |
| 目录模式 | 三模式行为与 `provisioningStatus` 一致；`create_new` 遇已存在目录报冲突 |
| 创建失败补偿 | 事务失败后新建的空目录被移除，既有目录保留 |
| 目录恢复 | 遗留日志 + 空目录 + 无项目引用 → 被清理；有引用 → 保留 |
| Agent 权限 | 无 `projects.create` 拒绝；有则通过；`scope=readonly` 拒绝 |
| 授权范围 | 自动授权只覆盖新项目；不能读其他项目 |
| 旧数据兼容 | 仅计划存在时反解析并补建项目根 |
| 四入口一致 | MCP / CLI / REST 返回同一 `projectId` / `activePlanId` |

前端（Vitest）：Workbench 快速创建（含三种模式与错误反馈）、ProjectHub 高级创建、两入口结果一致、
连续创建两个项目、创建后自动选中、超时重试不重复建项目。

集成（Dev 实例）：人类 UI 创建 → Agent 读项目 → Agent 建任务 → Agent 改规划 → 人类看到变化；
Agent 创建项目 → 拿到 canonical `projectId` → 自动获得授权 → 继续建任务。
