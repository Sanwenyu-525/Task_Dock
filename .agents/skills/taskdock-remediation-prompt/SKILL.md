# task_dock：证据驱动的修复任务生成

## 触发与边界
- **用户请求提示词**时使用；单纯验收不自动写长提示词；用户说“直接修复”则应实施而非只产提示词。
- 提示词不是已执行修复。先读根 `AGENTS.md`、相关代码、用户原始需求与（若有）当次验收证据；无法访问仓库时坦白说明，要求目标 Agent 自主定位。
- 永远拆分“已证实现象 / 用户期望 / 推测根因 / 未验证”。不能把旧报告中的猜测写成确定事实。

## 生成步骤
1. 汇总 **问题、复现前提、预期与实际、证据、优先级、范围外事项**；若刚做完验收，直接复用验收报告，不无必要重新扫描全库。
2. 对照 [references/handoff-schema.md](references/handoff-schema.md) 提取可机器处理的 finding；没有真实证据时标待确认。为适合重复生成的场景，可按 `assets/templates/findings.template.json` 填写 JSON，并用 `scripts/render_prompt.py` 生成**初稿**，再按仓库代码复核与补充；无需运行时直接按模板撰写。
3. 参照 [references/prompt-quality-gates.md](references/prompt-quality-gates.md) 检查是否包含实际根因排查、最小修改、兼容性/并行安全、正反验收与验证记录。
4. 强制要求执行 Agent：开工和交付 `git status`，保留其他会话修改，不强行清理缓存/终止未知进程；涉及 Tauri IPC、SQLite、Win32、剪贴板、Agent pipeline 时先核对现有契约。
5. 选择 A–F 验证层；F 的抢前台与鼠标移动需取得授权。结果只分“实际执行/静态审查/未执行/环境阻塞”。
6. 将最终**完整任务指令**作为一份可复制正文交付，不把大段模糊建议替代可验收行为。

## 输出必须包含
- 任务目标与明确非目标；背景与证据等级；先查的真实代码/若未知则搜索定位。
- 最小根因修复要求、需要保持的 API/迁移/用户数据/性能边界。
- 实施步骤、必要测试与 A–F 对应通道、失败判据、报告与文档位置。
- 最终报告：结论、修改路径、实际命令/退出码与时间、截图/指标、未验证及遗留风险。

输出模板在 `assets/templates/prompt.template.md`；当用户已授权直接修改代码，不要用本 Skill 的脚本生成文本冒充执行。
